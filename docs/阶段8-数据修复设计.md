## 1. 先别谈「删」：把错数据拆成三类

「这批数据有错，重跑一遍就好了」是这件事最常见、也最贵的误判。500 篇实测里能挑出的问题，
按**处置方式**分其实是三类，混在一起谈就必然选错工具：

| 类别 | 实例（日志里可数） | 条数 | 该做什么 |
|---|---|---|---|
| A 内容错 | `英伟达 --founded--> 黄仁勋`（宾语填了创始人）<br>`Entro --founded--> Simon Harrer`<br>`Fardesk --open_sourced--> Apache-2.0`（许可证不是产物） | 7 | 撤回 |
| B 同一事件多写法 | `Anthropic --funded--> 首次公开募股` / `--> IPO` / `--> IPO 募资` | 3 | 归一，**不撤回** |
| C 实体分裂 | `NVIDIA` 与 `英伟达` 是两行；`Grand Theft Auto VI` / `Grand Theft Auto 6` / `GTA6` 是三行 | 未统计 | 加指针，**不撤回** |

三类混谈会犯两个方向的错：

- **把 B 当 A 删掉**。那三条说的都是同一件事，每一条都是真的，删掉任何两条都是丢信息。
  真正的问题是查询时没把它们读成一条。
- **把 C 当 A 删掉**。`英伟达` 那半条时间线是好的，删了等于把这家公司砍掉一半。

所以第一件事不是「找出哪条错」，是**先把处置动作分类**。下面每个动作都要能单独执行、
单独回滚。

---

## 2. 约束先行：阶段 7 已经把方案空间砍到只剩「加指针」

设计数据修复时最容易想到的两条路，正好都被阶段 7 的约束堵死了：

```python
# apps/api/migrations/versions/0009_entities_fact_claims.py
IF NEW.object_text  IS DISTINCT FROM OLD.object_text     -- ① 改宾语
OR NEW.predicate    IS DISTINCT FROM OLD.predicate
OR NEW.valid_from   IS DISTINCT FROM OLD.valid_from
OR NEW.subject_id   IS DISTINCT FROM OLD.subject_id      -- ② 合并实体
OR NEW.document_id  IS DISTINCT FROM OLD.document_id
OR NEW.recorded_at  IS DISTINCT FROM OLD.recorded_at
```

① 堵死「把 `黄仁勋` 改成 `1993`」；② 堵死「把 `英伟达` 的事实挂到 `NVIDIA` 名下」。

唯一约束同样致命：键是 `(subject_id, predicate, object_text, document_id)`，
**认的是内容，不是行号**。所以「改完词表重跑一次」在数据库眼里是新增，旧行不动——
这正是 8.10 里说的「一库半新半旧」。

剩下的可行操作只有两种，而且都不移动数据：

| 操作 | 语义 | 落到哪 |
|---|---|---|
| 加一列标记状态 | 「这条我不认了」，但行还在、证据还在 | `fact_claims.retracted_at` |
| 加一个指针表达归属 | 「这行属于那个规范实体」 | `entities.merged_into` |

**这个约束不是障碍，是护栏。** 它把「修数据」从「改内容」逼成了「加标记」，
而后者天然可逆。下面两节就是这两个动作。

## 3. 动作一：撤回，不是删除

### 3.1 为什么不能拿 `valid_to` 表达撤回

表里已经有 `valid_to`，看起来「把错的那条闭合掉」就够了。不够，因为它属于**世界轴**：
「这件事什么时候不再成立」。

举个具体的错法：撤回 `OpenAI --ceo--> Sam Altman`（假设它是误抽的）时写
`valid_to = 2025-11-20`，那么 `as_of("2025-11-19")` 会回答「那天 CEO 不是 Sam Altman」。
**错的是我们这条记录，不是 2025 年 11 月的世界。** 用一个字段表达两件事，就会在 `as_of` 上
系统性地撒谎——而 `as_of` 恰恰是双时间表唯一存在的理由。

正确表达是：这条记录被我们在 2025-11-20 撤回，它在世界里是否成立，我们不再声称。

### 3.2 DDL 草案（迁移 0010）

```sql
ALTER TABLE fact_claims
  ADD COLUMN retracted_at          timestamptz,
  ADD COLUMN retracted_reason      text,
  ADD COLUMN retracted_replaced_by uuid REFERENCES fact_claims(id) ON DELETE SET NULL;

-- 撤回必须给出理由。没有理由的撤回就是一次不可审计的判断。
ALTER TABLE fact_claims
  ADD CONSTRAINT ck_fact_claims_retraction
  CHECK (retracted_at IS NULL OR retracted_reason IS NOT NULL);
```

第三列叫 `retracted_replaced_by` 而不是 `replaced_by`，是因为表里已经有一个
`superseded_by`——那个是世界轴（新事实取代旧事实，因为世界变了），两个名字长得像、
语义相反，迟早有人填错。加 `retracted_` 前缀让这三列在 `\d` 的输出里排在一起。

三列都不在触发器的禁止列表里，**所以不用改触发器**——这是刻意的：撤回改的是「我们信不信」，
不是「原文说了什么」。`retracted_replaced_by` 只在能确定对应关系时填（同一 `document_id` +
同一 `subject_id` + 同一 `predicate`），定不确定就留空。

### 3.3 查询侧：全过滤，但把数量说出来

`entity_timeline` 与 `as_of` 一律 `WHERE retracted_at IS NULL`——包括 `as_of` 里那条
查 `undated` 的附属查询。**只改主查询等于没改**：撤回项会从「有日期」这一侧消失，
又从「时间未知」那一侧冒出来，看起来过滤生效了，实际只是把问题挪了个列表。

三条配套规则：

- 撤回项**不能进入** `find_overlaps` 的冲突判定。否则一条已撤回的旧 CEO 会永远跟现任
  报冲突，把 `overlaps` 变成噪声源。过滤在 SQL 层做完，这条自动成立。
- **撤回条数必须返回**（`TimelineResult.retracted_count`）。全过滤之后，「撤过一条」和
  「从来没记过」的返回值完全一样，而这两件事含义相反：前者说明库里有东西、只是我们
  不再信；后者说明还没抽取。只加一个 `COUNT`，就能把这两种「空」分开。
- **暂时不开 `--include-retracted`。** 现在库里一条撤回都没有，为不存在的查询开一个
  参数，等于提前承担它的解释成本（模型会问「要不要加这个参数」，然后随机加）。等
  真的需要复盘「这条为什么被撤」时再加，那时也才知道该返回内容还是只返回理由。

工具层对应地改两处文案：全部被撤回时不能回答「这个实体没有任何事实记录」（那是
「还没抽取」的意思），要说清是「全部已撤回，不可作为回答依据」。

### 3.4 判错的代价：这是选撤回而不是删除的**唯一**理由

| | 删除 | 撤回 |
|---|---|---|
| 判错了怎么恢复 | 只能重跑那一篇，结果还不一定一样（温度 0 也不稳定，见 8.3） | `UPDATE retracted_at = NULL` |
| 证据链 | 跟着行一起消失 | 原文片段还在 |
| 能否审计「谁撤了什么」 | 不能 | 能，`reason` + `retracted_at` |
| 实现成本 | 一行 `DELETE` | 一列 + 一个过滤条件 |

注意最后一行是**反过来的**：删除更便宜、更快、更「干净」。选撤回不是因为它更好写，
是因为这批数据的错误率大约 3%（7/238），而**判定本身不可靠**（见第 5 节）。
在判定不可靠的前提下做不可逆操作，等于赌。

### 3.5 一个反直觉的后果，必须写进文档

撤回之后重跑同一篇文档，模型如果**又一次**抽出完全相同的那条错记录，`ON CONFLICT DO NOTHING`
会静默跳过它——行还在，撤回状态保留。

这是想要的（人工判断不该被重跑覆盖），但它的表现是「跑了两遍，这条还是没出来」。
不写清楚，下一个人会把它当 bug 查半天。

### 3.6 反过来那一半：什么时候该写 `valid_to`（迁移 0013）

第 3.1 节把两条轴拆开了，但只兑现了认识轴那一侧。世界轴这一侧一直空着：
`valid_to` 从 0009 起就在表里，触发器也一直允许改它（禁止列表里没有它），
**但没有任何代码写过它**。270 条事实因此全是「至今成立」。

代价在实体合并之后立刻显形：`英伟达` 名下 `Jensen Huang` 与 `Colette Kress` 两条
`ceo` 都没有结束日，于是「两人同时在职」。这不是脏数据——一条证据写
`former CEO Jensen Huang`，另一条写「原CFO Colette Kress 接任临时CEO」，**两条都对**。
所以撤回在这里是错的：撤哪一条都会丢掉一个真实的人事状态，而且撤完
`as_of("2026-03-01")` 会回答「当时不是他」。

正确的动作是给前一条补结束日。这带来一个设计问题，和 `aliases` 正好相反：

| | `aliases` | 允许徒手改 `valid_to` |
|---|---|---|
| 形态 | 有列、被读、**没人写** | 有列、能写、**谁都能写** |
| 后果 | 等于没有 | 填错一天不报错，只在某个历史时点答错，而**没人会去看那一天** |

所以迁移 0013 加的不是写入逻辑，是**一个理由列加一条 CHECK**：
`valid_to IS NULL OR valid_to_reason IS NOT NULL`。这条约束和撤回那条同构，
区别只在轴：撤回是「我们什么时候不再声称」，闭合是「这件事什么时候不再成立」。
合在一列里，等于把「记错了」和「世界变了」压成同一个状态，`as_of` 又会开始撒谎。

写入方是 `repair_facts.py supersede`，四个判据全部在碰库之前算完（纯函数
`plan_closure`，19 条测试里 15 条钉的是它）：

| 情形 | 处置 | 为什么不能放过 |
|---|---|---|
| 两条谓词不同 | 拒绝 | 「世界变了」只发生在同一个谓词上：不能用一条融资记录闭合一条人事记录 |
| 拿不出闭合日（两条都没有 `valid_from`） | 拒绝，要求 `--on` | 默认「今天」就是拿采集时间冒充世界时间 |
| 闭合日 ≤ 旧行 `valid_from` | 拒绝 | 区间退化，0009 的 `period` CHECK 也会拒 |
| 旧行已经闭合在别的日期 | 拒绝，要求先 `--undo` | 直接改日期等于悄悄重写一段历史，连「有人改成过什么」都不留 |

三个实现细节值得单独记：

- **默认闭合日取继任者的 `valid_from`。** 不是「今天」，也不是「旧行的最后一条报道」。
  理由很直接：「旧的不再成立」和「新的开始成立」是同一个分界，取同一个日期，两条区间
  正好接上，冲突归零且不留空档。显式 `--on` 与它不一致时，脚本会**警告会留出空档**
  而不是拒绝——因为真实世界里确实存在空窗期。
- **同组判定比的是合并组，不是 `subject_id`。** 合并是写指针，外键不动，
  所以 `Nvidia` 与 `英伟达` 名下的事实仍是两个 `subject_id`。比 id 会把唯一真实的
  用例挡在门外。
- **`--undo` 一次清三列。** `valid_to` / `valid_to_reason` / `superseded_by` 是同一个
  判断的三个部分，只清一个会留下一条「有指针但没结束日」的记录，比没改过更难解释。
- **候选对由 `--list` 算，不靠人抄 uuid。** 第一版的做法是贴一条 `SELECT … WHERE
  predicate='ceo'` 再抄两个 36 位字符串。它失败过两次，而且**一次都没报错**：`--id`
  与 `--by` 抄反时，被闭合的是现任的任期，脚本照样打印「已闭合」；在 Docker Desktop
  的 Exec 终端里，粘贴被括号粘贴标记 `^[[200~` 打断，psql 报的是一句与原因无关的
  `syntax error`。所以聚合、去重、配对都进脚本：按合并组（不是 `subject_id`）、
  只取单值谓词（`partnered_with` 六条会产出 `C(6,2)=15` 条假候选）、只配相邻两条
  （三条依次在任要闭合 `(A,B)` 与 `(B,C)`，拿 A 对 C 会让中间那段任期消失）。
  每对候选都跑一遍 `plan_closure`，能闭合的打印整条命令，不能的把理由打在旁边。

`superseded_by` 这一列也因此第一次有了写入方。它从 0009 起就存在，和 `aliases` 一样
「有列、没人写」——差别只是这次判断标准先成熟了，指针才敢往上写。

## 4. 动作二：实体分裂只能靠指针并

### 4.1 为什么必然分裂

`resolve_or_create_entity()` 按 `canonical_key` 建行，而 `normalize_key()` 只做
「小写 + 只留字母数字与汉字」：

```python
normalize_key("NVIDIA")  == "nvidia"
normalize_key("英伟达")  == "英伟达"   # 汉字保留，跟 nvidia 毫无关系
```

唯一约束是 `(kind, canonical_key)`，所以英文名和中文名**必然**是两行。这不是 bug，
是「不做跨语言对齐」这个简化在数据上的直接投影。

### 4.2 现成的 `aliases` 为什么救不了

`entities.aliases` 这一列存在，`resolve_entity()` 也读它：

```python
if any(normalize_key(alias) == key for alias in (entity.aliases or [])):
    return entity
```

但整个仓库**没有任何代码往里写**（`grep aliases` 只有这一处读、一处建表）。而且就算写了，
也修不好，原因有两层：

1. `resolve_entity()` 返回的是**单个**实体，`entity_timeline()` 又只查
   `FactClaim.subject_id == entity.id`。别名让「用中文名能查到英文实体」，但查不到
   **挂在另一个 id 上的那些事实**。
2. 事实是抽取时按当时的写法分头落库的：`NVIDIA` 的发布记录挂在 A 行，
   `英伟达` 的合作记录挂在 B 行。别名写在 A 上，B 的那些记录依然不在结果里。

换句话说：**别名解决的是「用哪个名字能命中」，不是「命中之后拿到谁的事实」。**
这两件事在阶段 7 被同一列承载，是设计上的一处混淆。

### 4.3 `merged_into` + 闭包展开（迁移 0012）

```sql
ALTER TABLE entities
  ADD COLUMN merged_into uuid REFERENCES entities(id) ON DELETE SET NULL;

-- 自指直接拒。多跳环路只能靠代码里的深度上限兜，SQL 的 CHECK 看不到别的行
ALTER TABLE entities
  ADD CONSTRAINT ck_entities_not_self_merged CHECK (merged_into IS NULL OR merged_into <> id);
```

查询侧把「一个实体」换成「一组 id」：

```python
async def resolve_entity_group(session, name) -> list[Entity]:
    root = await resolve_entity(session, name)          # 复用现有逻辑
    if root is None:
        return []
    # 沿 merged_into 向上找根，再向下收集所有指向该根的行；深度上限 8 防环
    ...
```

`entity_timeline` 改成 `subject_id IN (group)`，`as_of` 与 `find_overlaps` 同理。

**不用 `UPDATE ... SET subject_id` 的原因**：触发器不允许，而且改完就再也查不到
「这条事实当初是挂在 `英伟达` 这个写法下的」。指针并保留了分裂的历史，
合并是可逆的（清空 `merged_into` 就还原）。

实现细节里有三处是设计时没写、写的时候才定下来的：

| 决定 | 理由 |
|---|---|
| 允许链式（A→B→C），不要求只指根 | 合并是分批做的：先并 `英伟达`→`NVIDIA`，之后才发现 `NVIDIA Corp` 也该并。要求只指根会把这件事变成必须改历史数据 |
| 深度上限 8，环路停在当前行而不抛 | 坏指针不该让整条时间线变成 500。但必须保证它**会停**——`CHECK` 只能拦自指，看不到别的行 |
| 结果里点名 `merged_names` | 「这家公司只有 3 条事实」和「它其实有 9 条，另外 6 条挂在另一种写法下」在回复里读起来一样，而后者被当成前者就会漏引一半 |

写入方只有一个：`repair_facts.py merge --id <被并的行> --into <根> [--undo]`。
**这一条是补 `aliases` 的坑**——那一列存在、也被读，但整个仓库没人往里写，等于没有。
`merge` 在写之前先算一遍会不会成环（从 root 沿链往上走，撞见 dup 就是成环），
因为环路一旦写进库，向上找根就只剩深度上限硬停，那时已经没人知道哪一行是真的根。

全量现状：199 个实体，`英伟达` 名下 9 条事实、`Nvidia` 名下 4 条。合并后一次查询
能拿到 13 条，`as_of` 也会第一次看到这两边的 CEO 记录放在一起判冲突。

### 4.4 副作用：`overlaps` 会开始报跨写法的冲突

合并前，`NVIDIA` 和 `英伟达` 各自只有一半事实，两边的「同期两任 CEO」永远碰不上。
合并后它们会进同一次冲突判定——**这正是想要的**。实跑（2026-11-21）结果：

```
合并前  英伟达 9 条 / Nvidia 4 条，各自算冲突
合并后  13 条，conflicts = 18
```

18 这个数当时看着就像「发现了一堆旧问题」，实际不是。拆开只有 3 条是真信号：

| 谓词 | 条数 | 判出 | 性质 |
|---|---|---|---|
| `partnered_with` | 6 | 15 | **纯噪音**：台积电、富士康、安靠、矽品、景硕、三星电机可以同时都是伙伴 |
| `ceo` | 2 | 1 | 真冲突 |
| `founded` | 2 | 1 | 真冲突（`黄仁勋` / `1993` 槽位错位） |
| `discontinued` | 2 | 1 | 同一件事的中英文两条 |

根因是 `find_overlaps` 把**所有**谓词都当单值谓词。而渲染层只显示前 5 条，于是
15 条噪音把 3 条真信号全部挤出了视野——**多报的代价不是「多看几行」，是真信号被埋。**
修法是给谓词分单值/多值（`MULTI_VALUED_PREDICATES`），名单外一律按单值处理：
漏报的表现是「两条矛盾并存却没人提示」，比噪音危险得多。修完 18 → 2；
再撤回 `founded` 填人名的 4 条（`英伟达 --founded--> 黄仁勋` 就在这 2 条里）→ 1。

最后剩下的 1 条是 `Jensen Huang` 与 `Colette Kress` 同时「至今在任」。
**两条都不是错的**：证据里一条写 `former CEO Jensen Huang`，另一条写「原CFO Colette
Kress 接任临时CEO」。它们冲突是因为 `valid_to` 全为空——前任的任期没有结束日。
这类冲突不能靠撤回解决，撤哪条都会丢掉一个真实的人事状态，正确处置是补 `valid_to`
（任务清单第 9 步）。

- 冲突数会先上升再下降。上升是发现旧问题，不是引入新问题。
- **名单是手写的，所以一定会漏第二次。** `supersede --list` 首跑 7 对候选、0 对可
  闭合，其中 6 对是 `released_version` 被当成单值：`nginx 1.30.7`/`1.31.9`（稳定线
  与主线并行）、`DaisyRose-27B` 的 `BF16`/`FP8`/`NVFP4`（同模型三种权重）、
  `GPT-6.2` 的 `Astra`/`Sol`（并列变体）。判据不是「名字像就多值」，而是**这个谓词
  说的是「发布过某版本」（存在性）还是「当前版本是某版本」（唯一性）**。
  改名单时先问这句话，比逐个谓词套常识可靠。
- **同日候选不能给箭头。** `--list` 里日期相同的两条按 `object_text` 字母序排列，
  于是 `ceo` 那组打印成「Colette Kress → Jensen Huang」，方向恰好相反。现在同日只报
  「A / B」并说明方向不作数——一条方向错的箭头比没有箭头更糟，人会照着它闭合。
- 同一件事可能在同一实体的时间线上出现两次（两篇文档各抽一次，写法不同）。
  这属于第 1 节的 B 类（多写法），合并之后才有机会看到，也才有机会归一。
  本次实跑就撞到一条：`discontinued` 的 `AI chip sales to China` 与
  `对华 AI 芯片销售` 来自**同一篇文档**，只因主语被识别成两种写法而各存一行。
  唯一约束含 `subject_id`，所以它在合并前根本挡不住。

### 4.5 它是缺陷一的前置条件

8.10 提到的「对称谓词只挂一侧」，修法是填 `object_entity_id`。但**宾语本身可能就是个
分裂实体**（`英伟达 --partnered_with--> 台积电` 里的两个名字都可能有两种写法）。
在没有 `merged_into` 的情况下填外键，等于把宾语解析到两个等价行中的任意一个——
于是「有些能双向、有些不能」变成「有些双向到 A 行、有些双向到 B 行」。

所以顺序是硬的：**先有 `merged_into`，再谈填 `object_entity_id`。** 反了就得返工。

## 5. 判定标准：三档，只有一档能自动

这是整份设计里最需要诚实的地方。直觉上「错数据」应该能被规则批量挑出来，
实际上只有一类可以。

| 档 | 判据 | 能否写死 | 设计时估的条数 | 实跑（270 条） | 处置 |
|---|---|---|---|---|---|
| ① 形状不符 | 宾语是许可证标识符（没有任何谓词把许可证声明为合法宾语） | 能，正则 | 2 | 3 | 自动撤回 |
| ② 看宾语就知可疑 | `founded` 的宾语填了人名；`funded` 的宾语填了投资方 / 被投方 / 贷款 | 不能，但可批量只读判定 | 4 | 8 | 人工队列，逐条裁决 |
| ③ 必须拿证据对照 | 把 CFO 写成 CEO、收购方向反（谁买谁） | 不能 | 1 | **1（假阳性，见 5.3）** | 人工 |

实跑比预估多出 4 条，全部在 `funded` 上——抽样时只看了 `founded`，同一类槽位错位
在 `funded` 上更普遍：`深微芯创 --funded--> 深产投`（宾语填了投资方）、
`英伟达 --funded--> 矽品精密`（方向反了）、`胜宏科技 --funded--> …贷款承诺函`（债务当股权）。
不影响结论，但说明**判据必须对全量数据跑一遍，抽样的覆盖率比感觉上低**。

① 档的 3 条里，第 3 条是**撤回执行完才发现的**，原因见 5.2。

② 与 ③ 的区别不在难度，在**判据来源**：② 的疑点就在宾语上——`founded` 要的是年份或机构，
而宾语填了「黄仁勋」，不用看原文就能起疑；③ 的宾语形状完全正常（`Colette Kress` 就是个人名），
只有把 `predicate` 与 `evidence_text` 摆在一起看才发现矛盾。

**但 ③ 档这一条实跑是假阳性，而且错得很典型。** 规则看到证据里有 `CFO`，就判「把 CFO 记成了
CEO」；原文是「这是**原CFO** Colette Kress 接任临时CEO以来」——`原CFO` 恰恰是「曾经是 CFO、
现在不是」，方向与规则的读法相反。同组另一条 `Nvidia --ceo--> Jensen Huang` 的证据写的是
`After former CEO Jensen Huang`。两条串起来：黄仁勋卸任 → Kress 接任临时 CEO，
**这条 CEO 事实完全正确**。

所以 ③ 档的真实命中率是 **0 条，不是 1 条**。结论要写在这里，因为它直接决定第 7 节的优先级：

> 关键词命中不等于命题成立。③ 档一旦写成关键词规则，就退化成 ② 档，
> 而且是 ② 档里最差的那种——看起来有证据支撑，实际只匹配了词形。

真问题被这条假阳性带出来了：两条 CEO 事实的 `valid_to` 都没填。黄仁勋的任期早结束了，
记录却说「至今」。冲突信号是对的，但它指的不是「某条事实错了」，而是「时间轴不完整」。
撤回任何一条都会丢掉真实信息（一个前任、一个现任），正确处置是补 `valid_to`，不是撤回。

**泛称宾语（`--benchmark--> leaderboard`、`公共 MCP 注册表`）三个档都不进。** 它读起来别扭，
但不改变「谁在什么时候做了什么」的判断，而且数量大（benchmark 密集的论文一篇能出十几条）。
正确处理是让 `object_type` 在**抽取期**挡掉（第 7 节），不为它回补历史。

**注意 ① 只有 3 条。** 270 条里能自动修的刚过 1%。这不是设计失败，是这件事的真实形状：

> 能被确定性代码判定的，只有「形状」；「意思」对不对，代码判不了。

而这恰恰是第 3 节选撤回的原因——既然判定能力只有这么点，就必须让判错的代价接近零。

### 5.2 撤回之后才发现的那一条：正则锚死了结尾

第一版 ① 档正则带了 `$`：

```python
LICENSE_RE = re.compile(r"^(?:Apache|MIT|AGPL|…)[- ]?\d?(?:\.\d)?$", re.I)
```

它只认「宾语**正好等于**许可证标识符」。撤回完 `Windshift --open_sourced--> AGPL-3.0`
之后去核对时间线，发现同一篇文章里还留着一条：

```
Windshift  open_sourced -> AGPL-3.0 单二进制
```

原文是 `a single AGPL-3.0 binary`——同一个错误，只因为宾语后面跟了三个字的限定语，
就从 ① 档整个漏了过去。**两个条目内容相同、处置相反，这个不一致比错判更糟**：
它让「已撤回」看起来像做了一半。

修法的关键在**放宽哪一头**：

- 放宽**尾部**：许可证后面允许跟白名单内的限定语（`单` / `二进制` / `许可证` /
  `license` / `源码` / `only` …），命中仍算 ① 档。
- 绝不放宽**首部**：一旦「以许可证名开头就算」，`MIT Media Lab`、`Apache Airflow`、
  `BSD 套接字` 这些正常宾语会被自动撤回——而 ① 档是唯一会**自动执行**的档位，
  误撤没有第二双眼睛拦得住。

用白名单而不是「尾巴够短就算」，也是同一个理由。这条规则对全量 267 条重跑，
① 档只多出那一条，没有产生任何假阳性——**放宽一个约束之后必须重跑全量，
因为新增的命中里既有漏掉的真相，也有新造的假阳性，两者只能靠数据分辨**。

### 5.1 为什么「意思不符」不自动撤：举证责任在撤回方

一条自动规则的误判率哪怕只有 5%，乘上「批量」就是几十条真实信息被抹掉，而抹掉之后
**没人会知道少了什么**（时间线少一条，看起来就是没发生）。所以：

- 自动撤回只用于**形状**：宾语是 `Apache-2.0`——任何谓词下它都不该出现在这个位置，
  这不是判断题，是格式检查。
- 涉及语义的一律进队列，撤回时必须附**原文片段**。理由不附证据，撤回本身就成了
  新的不可审计判断——和当初模型编造事实是同一种病。

### 5.2 ① 档的可执行判据

```python
LICENSE_RE = re.compile(
    r"^(?:Apache|MIT|BSD|GPL|AGPL|LGPL|MPL|EPL|ISC|Unlicense|CC[- ]BY)"
    r"[- ]?\d?(?:\.\d)?(?:[- ]only|[- ]or[- ]later)?$",
    re.IGNORECASE,
)


def is_shape_violation(object_text: str) -> str | None:
    """返回撤回原因，或 None。只判形状，不判语义。

    注意这里**不豁免 open_sourced**：许可证是「以什么条件开源」，是条件不是产物。
    `Fardesk --open_sourced--> Apache-2.0` 的正确写法是宾语填被开源的仓库名，
    `evidence_text` 里那句话已经交代了许可证。豁免它，恰好会放过唯一真实的违规。

    也不要给它加 predicate 参数：一旦按谓词分支，它就变成判断题了。
    """
    if LICENSE_RE.match(object_text.strip()):
        return "object_is_license"
    return None
```

这一条能写成死代码，是因为它不涉及「这条事实对不对」，只涉及「这个位置能不能放这种东西」。
凡是需要判断「对不对」的，都进 ② ③。

### 5.3 ② 档怎么让它可复核而不是可变通

队列不是「人肉看 238 条」，而是让模型做一次**只读、带原文**的判定：

- 输入：`(subject, predicate, object, evidence_text)` 四元组，不喂全文
- 输出：`keep` / `retract` + 一句理由
- 只对**宾语形状可疑**的子集跑（人名、泛称、数字），不到 20 条
- 结果落 `scripts/repair_facts.py audit --format csv`，人工过一遍再执行

关键约束：**这个脚本不能直接写库。** 判定与执行分离，不然就是「让模型给自己判卷」。

### 5.4 ③ 档只能缩小范围，不能自动化

③ 档原本举的例子就是 `英伟达 --ceo--> Colette Kress`：宾语形状完全正常，疑点在「她是 CFO」。
要发现它，唯一的办法是把 `predicate` 和 `evidence_text` 摆在一起看。

**实跑之后这个例子作废了，见 5.3 末尾：那条事实是对的。** 原文「原CFO 接任临时CEO」里，
`原CFO` 是「曾经是 CFO」，规则的读法正好读反。而它当初被报出来，正是因为规则只匹配词形。
这件事说明 ③ 档的边界比想象中更窄：

> `evidence_text` 是模型当初用来「证明」这条事实的原文。拿它去反证，前提是**读懂句子结构**，
> 而不是在里面找关键词。关键词匹配版本的 ③ 档，产出的是看起来有依据的误报。

可以做的只有一件事：把 ② 的队列机制复用一次，输入换成 `(predicate, object, evidence)`，
让判定方回答「证据支持这个谓词吗」——由人或模型读完句子再答，而不是让正则数词。
但仍然**不进自动撤回**——它判的正是「意思对不对」，而第 5.1 节说过这类判断的
误判是不可见的。本次这条误报正好是这句话的实证：一条被判「内容错」的事实，
证据原文里其实写着它是对的。

## 6. 重跑怎么才能不产生半新半旧

有了撤回，「改词表 → 重跑」才第一次变得安全。规则是三条**同时**满足才替换：

| | 条件 | 为什么 |
|---|---|---|
| 1 | 同一 `(document_id, subject_id, predicate)` | 跨文档不能互删，那可能是两件不同的事 |
| 2 | 旧记录的 `object_text` 被判定违规（① 或 ② 档） | 只替换「已判定错」的，不替换「看起来重复」的 |
| 3 | 新记录 `evidence_match == exact` | 替换方必须比被替换方更硬，否则是拿猜测换事实 |

任一条不满足就只插入、不撤回。这条纪律的代价是「会有少量重复」，收益是
**永远不会因为重抽而丢失一条本来对的记录**——而后者不可恢复。

## 7. 词表：把 `object_type` 变成结构，不是文案

8.10 缺陷三的根因是词表只有两个字，宾语类型从来没写出来过。修法不是把文案写长
（那还是一次自然语言约定，prompt 与校验还会漂移），是给它一个结构：

```python
@dataclass(frozen=True, slots=True)
class PredicateSpec:
    label: str
    object_type: Literal["entity", "person", "year", "version", "metric"]
    cardinality: Literal["single", "many"]   # ceo/founded 单值，released 多值

PREDICATES: dict[str, PredicateSpec] = {
    "ceo":        PredicateSpec("CEO 由谁担任", "person", "single"),
    "founded":    PredicateSpec("创立",        "year",   "single"),
    "open_sourced": PredicateSpec("开源",      "entity", "many"),
    ...
}
```

两个用法必须来自**同一份 spec**，否则又会出现「prompt 说 A、校验判 B」：

- 抽取 prompt 由 spec 渲染出「宾语类型」表格，不再手写
- 落库校验按 `object_type` 判形状（① 档的判据因此从正则白名单升级成类型检查）
- `cardinality == "single"` 的谓词出现同期多值时，**只报警不撤回**，交给 `overlaps`

**改 spec 不会影响已入库的 238 条**——这是好事，也是为什么必须先有撤回：
词表升级只对未来的抽取生效，已有的错记录只能靠第 5、6 节处理。

## 8. 执行顺序与验收

顺序不能换。理由在第 3 节：**撤回通道必须先于判定标准存在**，否则判错一次就没有退路。

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | ✅ 迁移 0010：`fact_claims` 三列 + 一 CHECK | `make test` 266 绿；`make migrate` 后 `\d fact_claims` 能看到新列 |
| 2 | ✅ 查询侧过滤（含 `undated` 附属查询）+ 撤回计数；暂不开 `--include-retracted` | 撤回项不进时间线、不进 `overlaps`；工具结果里报出撤回条数 |
| 3 | ✅ 迁移 0011：`documents.facts_extracted_at` + `pick_documents` 排除已判定的 | 重跑统计行出现「已标记 N 篇」，第二轮的 `重复` 接近 0 |
| 4 | ✅ `scripts/repair_facts.py audit`（只读） | 实跑 3 / 8 / 1 共 12 行 CSV；**此步不写库**；③ 那 1 条事后证明是假阳性 |
| 5 | ✅ `repair_facts.py retract --id ... --reason` | 3 条 ① 档全部撤回；`Windshift` 归零后工具层答「2 条已全部被撤回」，不是「没有事实记录」 |
| 6 | ✅ 迁移 0012：`entities.merged_into` + 闭包查询 + `repair_facts.py merge` | 查 `Nvidia` 与 `英伟达` 拿到同一组 13 条事实；结果里点名合并了哪些写法 |
| 7 | `PredicateSpec` 重构 + prompt 由 spec 渲染 | 抽取 prompt 里的宾语类型与代码判定一致 |
| 8 | 按第 6 节的三条前置条件定向重跑 | 替换数 ≤ 判定违规数；无一条 `evidence != exact` 的替换 |
| 9 | ✅ 迁移 0013：`valid_to_reason` + 闭合 CHECK；`repair_facts.py supersede --id 旧 --by 新` | 合并后 `英伟达` 的 CEO 冲突从 1 条降到 0 条，且两条事实都还在（一个前任、一个现任）；闭合日填晚一天时冲突仍在（`test_closure.py` 钉住这个失败模式） |

第 9 步是实体合并跑出来的，不是设计时想到的。合并后 `英伟达` 只剩 1 条冲突：
`Jensen Huang` 与 `Colette Kress` 同时「至今」。两条都**不是错的**——证据里一条写
`former CEO Jensen Huang`，另一条写「原CFO Colette Kress 接任临时CEO」。
它们冲突是因为 `valid_to` 全为空，前任的任期没有结束日。**这类冲突不能靠撤回解决**：
撤哪一条都会丢掉一个真实的人事状态。这是双时间表只填了一半的直接后果。

落地时多了一个设计决定（见 3.6）：光有 `valid_to` 不够，还要一条理由列加一条 CHECK。
原因是「允许徒手改日期」和「有列没人写」是同一个毛病的两面——前者更危险，
因为日期长得像客观事实，填错一天没有任何信号。

这一行还留下一个必须说清的边界：**闭合的是区间，不是「他不再是 CEO」这件事。**
`as_of("2026-11-17")` 返回黄仁勋、`as_of("2026-11-18")` 返回 Kress，两个答案都来自
同一次查询语义，而不是两次人工判断。半开区间（`valid_from <= on < valid_to`）是
`as_of` 从阶段 7 就写死的约定，这里只是第一次真的用到右端点。


第 3 步不是原计划里的内容，是执行到「定向重跑」时被统计行逼出来的：`抽出 238 条 /
入库 148 条 / 重复 90 条` 说明候选集根本没有「抽过没有」的记录，38% 的调用在重抽同一批
文档；而 342 篇「无事实」文档因为没有任何事实行，连事后反推都做不到，每轮都要重判一次。
**没有这个状态位，第 8 步的定向重跑会先把预算烧在已经判过的文档上。**

第 5 步的验收是整份设计的核心断言：**撤回一条 CEO，`as_of("2025-11-19")` 的答案不能变。**
如果它变了，说明 `valid_to` 与 `retracted_at` 又被混用了。

## 9. 明确不做的四件事

| 不做 | 理由 |
|---|---|
| 整表重抽 | 33 分钟换来「一库半新半旧」：唯一约束只保证不重复，不负责清理，旧错行原样留着 |
| 自动判「语义一致性」（方向反、主体错位） | 需要外部知识，误判不可见；收益 1 条，风险全表 |
| 给 `retracted_at IS NULL` 加 partial 索引 | 270 行里只有 11 行被撤回，这个 partial 索引等于把 96% 的行再抄一遍，planner 不会用。等十万行再说，那时只换索引不换查询 |
| 顺手修 70% 的兜底日期 | 那是数据源问题（8.7 第三节），不是数据修复问题。混进来会让这一阶段永远做不完 |
