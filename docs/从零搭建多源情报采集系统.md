# 从零搭建多源情报采集系统：按开发阶段拆解的实战教程

## TL;DR

这份文档用一个真实跑通的系统（DevInsight AI）作样本，把「多源信息采集 → 标准化 → 入库 → 接口 → 页面」这条链路按开发阶段拆开讲。每个阶段讲三件事：**为什么要这样设计、代码怎么写、怎么证明它真的对**。读完你能照着复刻一套同类系统，也能看懂别人写的采集项目为什么那么写。

## 你将学到什么

- [ ] 用 Docker Compose + Makefile 把本地环境做成「一条命令起得来」的工程骨架
- [ ] 设计来源注册表与采集账本，让「哪一轮发生了什么」可回答
- [ ] 写一个生产可用（而不是 demo 可用）的 RSS 采集器：重试、限流、清洗、去重
- [ ] 用数据库唯一约束实现幂等入库，重复采集不污染数据
- [ ] 用 Celery 做「按来源各自节奏」的调度，而不是固定全量轮询
- [ ] 用游标分页替代 offset 分页，避免翻页时数据错位
- [ ] 在 Next.js 16 的缓存组件模型下正确组织数据获取，不在部署时踩坑
- [ ] 建立一套「怎么验证它对不对」的方法，而不是跑起来就算完

# 第 0 章 先建立全局图

## 0.1 一句话定义

这套系统的本质是：**把散落在几十个网站上、格式各异的公开信息，变成一张结构统一、可追溯、可检索的表。**

拆开就是四件事，顺序不能乱：

1. **取**：从各个来源把原始数据拿回来（RSS、API、网页）
2. **洗**：把每个来源不同的字段名、时间格式、HTML 标签，收敛成统一结构
3. **存**：幂等地写进数据库，重复采集不能产生重复数据
4. **看**：通过接口和页面把数据呈现出来，并且能看出「这条是几手信息、什么时候发的、什么时候采的」

四步里最容易做错的是第 2 步和第 3 步。第 4 步最容易做浅——只做了「显示」，没做「可追溯」。

## 0.2 数据流全景

```
定时器(Celery Beat)
      │ 每 5 分钟扫描：哪些来源到期了？
      ▼
任务队列(Redis) ──► Worker 取出任务
                        │
                        ▼
              Connector 抓取 + 解析
              （httpx 拿字节 → feedparser 解析 → 清洗 → 归一）
                        │
                        ▼
              CanonicalDocument（统一结构的内存对象）
                        │
                        ▼
         幂等写入 PostgreSQL（唯一约束兜底）
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   documents 表                   ingestion_runs 表
   （情报正文/元数据）             （这一轮采集的账本）
        │
        ▼
   FastAPI /api/v1/documents
        │
        ▼
   Next.js 页面（服务端取数 → 渲染）
```

注意这条链上有一个设计决定：**Connector 不碰数据库**。它只负责「抓 + 解析 + 归一」，往上一层交出统一对象。这样 Connector 可以单独写测试，不需要连库；换数据库、换写入策略都不影响它。

## 0.3 三条贯穿全项目的原则

后面每个阶段的具体写法，都是这三条原则的展开。

**原则一：幂等（Idempotent）**

同一个操作执行一次和执行十次，结果一样。采集系统必须幂等，因为网络会重试、定时器会重叠、你还会手动再点一次「同步」。实现手段是在数据库层加唯一约束，而不是在代码里先查再插——后者在并发下必然漏。

**原则二：时间双轨**

`published_at`（来源声称的发布时间）和 `fetched_at`（系统实际采集时间）必须是两个字段，永远不合并。没有可靠发布时间就留空，**绝不用采集时间顶替发布时间**。这不是洁癖：一旦混用，你就再也分不清「这条是三小时前发生的」还是「这条是三小时前才被我们抓到的」，而这两件事对情报判断的意义完全相反。

**原则三：可追溯**

每条数据都能回答三个问题：来自哪个源、原始链接是什么、哪一轮采集进来的。做不到这三点，数据量越大越不可信。

## 0.4 三个反直觉的决定

这三个决定当时看起来「多此一举」，后来都省了大事。

| 决定 | 直觉做法 | 实际做法 | 为什么 |
|---|---|---|---|
| 起步只接 3 个源 | 一次接 20 个显得功能全 | 先 3 个 RSS 打通全链路 | 20 个源同时调试，你分不清是解析问题还是写入问题 |
| 分页用游标不用 offset | `LIMIT 20 OFFSET 40` 最简单 | 用 `(排序值, id)` 做游标 | 采集是持续写入的，翻页时新数据插到前面，offset 会把同一条显示两次或漏掉 |
| 建表用 Alembic 不用 `create_all` | 一行 `create_all` 就建好了 | 写迁移脚本 | 改字段时 `create_all` 不会改已有表，你会得到一个「代码新、表旧」的诡异状态 |

# 第 1 阶段（手册阶段 0）工程骨架

**本阶段目标**：一条命令把环境起起来，前后端能通，数据库能连。

**验收标准**：`make up && make migrate` 无报错；`curl localhost:8000/api/v1/health` 返回 `status: ok`；页面能打开。

## 1.1 目录结构：为什么用 monorepo

```
devinsight-ai/
├── apps/
│   ├── api/            # 后端 FastAPI
│   │   ├── app/
│   │   │   ├── api/v1/       # 路由
│   │   │   ├── connectors/   # 各来源适配器
│   │   │   ├── core/         # 配置、日志、错误
│   │   │   ├── db/           # 引擎、会话、模型
│   │   │   ├── services/     # 业务逻辑
│   │   │   ├── utils/        # URL/时间/文本工具
│   │   │   └── worker/       # Celery
│   │   ├── migrations/       # Alembic
│   │   └── tests/
│   └── web/            # 前端 Next.js
├── docker-compose.yml
├── Makefile
└── .env                # 不入库
```

前后端放一个仓库的好处不是「看起来整齐」，而是**改动可以原子提交**：改了接口字段，同一个 commit 里把前端一起改掉，不会出现「后端已上线、前端还在读旧字段」的窗口期。个人项目尤其重要，因为你没有 CI 帮你守这个边界。

## 1.2 依赖服务：只要两个容器

```yaml
# docker-compose.yml
services:
  db:
    image: pgvector/pgvector:pg16
    # Docker Desktop / WSL 重启后容器不会自动回来，没有这条本地开发会莫名其妙连不上库
    restart: unless-stopped
    environment:
      POSTGRES_DB: devinsight
      POSTGRES_USER: devinsight
      POSTGRES_PASSWORD: change_me_dev
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U devinsight -d devinsight"]
      interval: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    ports:
      - "6379:6379"

volumes:
  pgdata:
```

三个细节值得单独说：

**为什么用 `pgvector/pgvector:pg16` 而不是官方 `postgres:16`。** 阶段 1 用不到向量，但阶段 5 要做语义检索。现在用带扩展的镜像，到时候只需 `CREATE EXTENSION vector`，不必重建数据卷迁移数据。同理，迁移脚本里也会先把扩展装上。

**`restart: unless-stopped` 不是可选项。** 这一条我踩过坑：Docker Desktop 重启后容器退出，`make sync` 报 `ConnectionRefusedError (127.0.0.1:5432)`。看起来像代码连不上库，实际是容器没起来，而且 `restart: no` 让它永远不会自己回来。排查了半小时才发现跟代码无关。

**`healthcheck` 让「启动完成」和「可用」不再是同一件事。** 容器 `Up` 不等于数据库能接受连接，`pg_isready` 通过才算。

> ⚠️ 密码 `change_me_dev` 是本地开发用的。这个文件如果进了公开仓库，改密码的同时记得 `docker compose down -v` 清卷，否则旧密码还在数据卷里。

## 1.3 Python 环境：依赖里那个不起眼的 greenlet

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

关键依赖及各自职责：

| 包 | 作用 | 少了会怎样 |
|---|---|---|
| `fastapi` / `uvicorn` | Web 框架与服务器 | — |
| `sqlalchemy[asyncio]` | ORM 与数据库抽象 | — |
| `asyncpg` | PostgreSQL 异步驱动 | 只能用同步驱动，异步代码全废 |
| `greenlet` | 让同步风格的 ORM 代码能跑在异步上下文里 | 报 `MissingGreenlet`，而且报错位置看起来毫无关系 |
| `alembic` | 迁移 | 只能手写 SQL 改表 |
| `psycopg[binary]` | 同步驱动，供 Alembic 使用 | 迁移无法执行 |
| `celery` / `redis` | 任务队列 | 只能手动跑采集 |
| `feedparser` | RSS/Atom 解析 | 要自己写 XML 解析，还要处理十几种时间格式 |
| `httpx` | 异步 HTTP | — |
| `tenacity` | 重试策略 | 重试逻辑要手写循环和睡眠 |
| `beautifulsoup4` / `lxml` | HTML 清洗 | 正则去标签会留下一堆实体字符 |

**为什么同时需要 asyncpg 和 psycopg。** 应用运行时用异步驱动（`postgresql+asyncpg://`），而 Alembic 的迁移执行是同步流程，用 psycopg（`postgresql+psycopg://`）。配置层专门写了一个属性做转换：

```python
# apps/api/app/core/config.py
@property
def sync_database_url(self) -> str:
    """同步驱动 URL，供 Alembic 与一次性脚本使用。"""
    return self.database_url.replace("+asyncpg", "+psycopg")
```

**greenlet 到底在干什么。** SQLAlchemy 的 ORM 是同步风格写的（`session.execute()` 返回结果对象），但底层是异步驱动。greenlet 提供「轻量协程切换」，让 ORM 在等 I/O 时可以挂起，等结果回来再继续。所以它是运行时依赖而不是可选优化。`MissingGreenlet` 这个报错的真实含义通常是：**你在没有 await 的上下文里触碰了需要 I/O 的属性**，比如在同步函数里访问了一个懒加载的关系字段。

## 1.4 Next.js 16 + Tailwind v4 的接线方式变了

用脚手架创建：

```bash
npx create-next-app@latest apps/web --ts --tailwind --eslint --app --src-dir
```

**但 Next 16 的 Tailwind 接线和 v3 时代完全不同**，这是最容易卡住的地方。旧教程让你建 `postcss.config.mjs` 并引入 `@tailwindcss/postcss`，而 Next 16 走 Turbopack，用的是 loader 方式：

```ts
// apps/web/next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,        // 缓存组件：默认开启，影响数据获取写法（第 2 阶段详述）
  partialPrefetching: true,
  turbopack: {
    rules: {
      "*.css": {
        loaders: ["@tailwindcss/turbopack"],   // 关键：CSS 交给这个 loader
        as: "*.css",
      },
    },
  },
};

export default nextConfig;
```

配套的是 `globals.css` 里一行 `@import "tailwindcss";`，没有 `tailwind.config.js`。

> ⚠️ 如果你从旧项目抄了 `postcss.config.mjs`，样式会「编译通过但全部不生效」——页面能打开，但没有一条工具类起作用。判断方法：看构建产物里有没有大段 CSS；或者随便给元素加 `bg-red-500`，不红就是没接上。

## 1.5 Makefile 作为唯一入口

个人项目最大的时间黑洞不是写代码，是**记命令**。`cd apps/api && ../../.venv/bin/python -m alembic upgrade head` 这种命令你一个月后一定记不住。所以把它固化成入口：

```makefile
# Makefile（节选）
SHELL := /bin/bash
# 用绝对路径引用解释器：相对路径会让 Python 解析出的 sys.prefix 带 ../..，
# Python 3.14 会为此刷 RuntimeWarning，污染每条命令的输出。
ROOT := $(CURDIR)
PY := $(ROOT)/.venv/bin/python
API := $(ROOT)/apps/api
WEB := $(ROOT)/apps/web

migrate: ## 执行数据库迁移到最新版本
	cd $(API) && $(PY) -m alembic upgrade head

sync: ## 立刻采集所有启用来源
	cd $(API) && $(PY) -m app.cli sync --all

status: ## 查看来源健康与最近批次
	cd $(API) && $(PY) -m app.cli list
```

三个真实踩过的坑，每一个都会让 Makefile 静默失效：

1. **缩进必须是真 tab，不能是空格。** 编辑器「把 tab 转空格」一开就废，报错是 `missing separator`，看不出哪里错。
2. **行尾必须是 LF，不能是 CRLF。** 在 Windows 上编辑会让 `#!/bin/bash` 变成 `#!/bin/bash\r`，报 `bad interpreter`。用 `.gitattributes` 锁死：
   ```
   * text=auto eol=lf
   *.png binary
   ```
3. **解释器别用相对路径。** `../../.venv/bin/python` 会让 Python 3.14 的 `sys.prefix` 变成 `/repo/apps/api/../../.venv`，与 `pyvenv.cfg` 里的绝对值不等，于是每条命令前面都刷两行 `RuntimeWarning`。用 `$(CURDIR)` 拼绝对路径解决。

还有一个容错设计值得抄：`up` 目标不是裸的 `docker compose up -d`，而是三级判断——docker 可用就正常启动；不可用但端口已在监听就跳过并提示；两者都不行才报错退出。这样当 Docker 客户端出问题时，不会用一个看不懂的 `Error 126` 掐断你整条 `&&` 命令链。

```makefile
up:
	@if docker version --format '{{.Server.Version}}' >/dev/null 2>&1; then \
		docker compose up -d && docker compose ps; \
	elif (exec 3<>/dev/tcp/127.0.0.1/5432) 2>/dev/null && (exec 3<>/dev/tcp/127.0.0.1/6379) 2>/dev/null; then \
		echo "✓ 5432 / 6379 已在监听，容器已运行，跳过启动"; \
	else \
		echo "✗ Docker 客户端不可用，且 5432 / 6379 都没有监听"; \
		exit 1; \
	fi
```

`exec 3<>/dev/tcp/host/port` 是 bash 内建的 TCP 探测，不依赖 `nc` 或 `telnet`，在没有外网工具的环境里很实用。

## 1.6 配置分层

优先级：**环境变量 > 仓库根 `.env` > 代码默认值**。`.env` 不入库，`.env.example` 只放占位符。

```python
# apps/api/app/core/config.py（节选）
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=(REPO_ROOT / ".env", API_DIR / ".env"),
        env_file_encoding="utf-8",
        case_sensitive=False,
        extra="ignore",
    )

    app_env: str = "local"
    database_url: str = "postgresql+asyncpg://devinsight:change_me_dev@localhost:5432/devinsight"
    http_user_agent: str = "DevInsightAI/0.1 (+contact: admin@example.com)"
    max_items_per_sync: int = 200

    @field_validator("database_url")
    @classmethod
    def _require_async_driver(cls, value: str) -> str:
        """强制使用 asyncpg 驱动，避免误用同步 URL 导致运行时才报错。"""
        if value.startswith("postgresql://"):
            return value.replace("postgresql://", "postgresql+asyncpg://", 1)
        return value
```

两个设计意图：

- **仓库根定位用向上查找**，不硬编码路径。找 `docker-compose.yml` 或 `.env` 作为标志，这样无论从哪个子目录启动都能读对配置。
- **校验器把错误提前**。如果 `.env` 里写了 `postgresql://`（同步写法），不校验的话错误会延迟到第一次查库才爆，堆栈还埋在 SQLAlchemy 内部。`field_validator` 让它在进程启动时就失败，报错指向配置本身。

# 第 2 阶段（手册阶段 1）来源注册与 RSS 闭环

**本阶段目标**：至少 3 个真实 RSS 源采集入库，可查运行日志，重复采集不产生重复数据。

**验收标准**：`make sync` 三个源全部 `succeeded`；再跑一次「新增 0、跳过全部」；`make status` 健康状态全部 `healthy`。

这是全项目最重要的一段。它不是「写个爬虫」，而是**建立一条生产可用的数据管线**。两者的区别在异常处理和数据一致性上。

## 2.1 先设计表，再写代码

四张表，各自回答一个不同的问题：

| 表 | 回答什么问题 | 关键约束 |
|---|---|---|
| `sources` | 有哪些源？现在健不健康？多久采一次？ | `source_key` 唯一 |
| `ingestion_runs` | 这一轮采集发生了什么？抓到多少、新增多少、多久、失败在哪？ | 外键 `source_id` |
| `documents` | 情报条目本身 | `UNIQUE(source_id, external_id)` |
| `source_health_logs` | 这个源的历史波动曲线 | 外键 `source_id` |

为什么不是两张表（source + document）就够？因为**「采集失败」和「没有新内容」在数据层看起来一模一样**——都是 documents 没变化。没有 `ingestion_runs`，你无法区分「这个源挂了三天」和「这个源三天没发新文章」。前者要报警，后者是正常的。

## 2.2 四张表逐张拆解

下面按「这张表回答什么问题」的顺序看，不要按建表语句的字段顺序看——后者只会让你记住拼写，记不住设计意图。

### sources：来源注册表

```python
# apps/api/app/db/models.py（节选）
class Source(Base):
    __tablename__ = "sources"
    __table_args__ = (
        UniqueConstraint("canonical_domain", "name", name="uq_sources_domain_name"),
        Index("ix_sources_health", "health_status", "enabled"),
    )

    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, server_default=text("gen_random_uuid()")
    )
    source_key: Mapped[str] = mapped_column(Text, nullable=False, unique=True)
    name: Mapped[str] = mapped_column(Text, nullable=False)
    canonical_domain: Mapped[str] = mapped_column(Text, nullable=False)
    source_type: Mapped[str] = mapped_column(Text, nullable=False)   # media / official / community
    region: Mapped[str] = mapped_column(Text, nullable=False, server_default=text("'global'"))
    access_method: Mapped[str] = mapped_column(Text, nullable=False)  # rss / api / html
    base_url: Mapped[str] = mapped_column(Text, nullable=False)
    rights_note: Mapped[str | None] = mapped_column(Text)
    credibility_tier: Mapped[str] = mapped_column(Text, nullable=False, server_default=text("'B'"))
    enabled: Mapped[bool] = mapped_column(Boolean, nullable=False, server_default=text("true"))
    poll_interval_minutes: Mapped[int] = mapped_column(Integer, nullable=False, server_default=text("360"))
    last_success_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    consecutive_failures: Mapped[int] = mapped_column(Integer, nullable=False, server_default=text("0"))
    health_status: Mapped[str] = mapped_column(Text, nullable=False, server_default=text("'unknown'"))
```

字段分四组理解，不要死记：

- **身份组**：`source_key`（代码里引用它，稳定不变）、`name`（展示名）、`canonical_domain`
- **行为组**：`access_method`（决定用哪个 Connector）、`base_url`、`poll_interval_minutes`、`enabled`
- **治理组**：`rights_note`、`credibility_tier`。这两列是**合规留痕**，不是装饰——采集别人的内容时，"允许存到什么程度"必须写在数据里，而不是记在脑子里
- **健康组**：`health_status`、`last_success_at`、`consecutive_failures`、`last_http_status`

`source_key` 单独存在的理由：主键是 UUID，会变；域名可能换；只有 `source_key` 是你代码和配置里能稳定引用的东西（比如 `36kr_zh`）。

### ingestion_runs：采集账本

```python
class IngestionRun(Base):
    __tablename__ = "ingestion_runs"
    __table_args__ = (Index("ix_ingestion_runs_source_started", "source_id", "started_at"),)

    source_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("sources.id", ondelete="CASCADE"), nullable=False
    )
    status: Mapped[str] = mapped_column(Text, nullable=False, server_default=text("'running'"))
    fetched_count: Mapped[int] = mapped_column(Integer, nullable=False, server_default=text("0"))
    created_count: Mapped[int] = mapped_column(Integer, nullable=False, server_default=text("0"))
    skipped_count: Mapped[int] = mapped_column(Integer, nullable=False, server_default=text("0"))
    http_status: Mapped[int | None] = mapped_column(Integer)
    duration_ms: Mapped[int | None] = mapped_column(Integer)
    error: Mapped[str | None] = mapped_column(Text)
    triggered_by: Mapped[str] = mapped_column(Text, nullable=False, server_default=text("'schedule'"))
```

四个计数各有含义，别合并成一个：

- `fetched_count`：这次响应里有多少条（来源说它有 200 条）
- `created_count`：真正新入库多少（去重后新增）
- `skipped_count`：命中唯一约束被跳过多少（重复）
- `updated_count`：更新了多少（阶段 1 恒为 0，因为策略是"不覆盖旧数据"）

判断健康与否的实用组合：`fetched > 0 且 created == 0` 且连续多次出现，通常意味着**这个源的内容不再更新**或**你的 external_id 取错了**（每条都被判为重复）。这个信号比"失败"更难发现，所以必须把计数分开记。

`triggered_by` 区分 `schedule`（定时）和 `manual`（手动），排查"数据突然变多"时先看这个。

### documents：文档表与那条唯一约束

```python
class Document(Base):
    __tablename__ = "documents"
    __table_args__ = (
        UniqueConstraint("source_id", "external_id", name="uq_documents_source_external"),
        Index("ix_documents_published", text("published_at DESC")),
        Index("ix_documents_fetched", text("fetched_at DESC")),
        Index("ix_documents_hash", "content_hash"),
    )

    source_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("sources.id", ondelete="CASCADE"), nullable=False
    )
    external_id: Mapped[str] = mapped_column(Text, nullable=False)
    canonical_url: Mapped[str] = mapped_column(Text, nullable=False)
    title: Mapped[str] = mapped_column(Text, nullable=False)
    summary: Mapped[str | None] = mapped_column(Text)
    topics: Mapped[list[str]] = mapped_column(JSONB, nullable=False, server_default=text("'[]'::jsonb"))
    # published_at 是来源声称的发布时间；fetched_at 是系统采集时间，二者不得混用
    published_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    fetched_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), nullable=False, server_default=func.now()
    )
    content_hash: Mapped[str] = mapped_column(Text, nullable=False)
    quality_flags: Mapped[list[str]] = mapped_column(JSONB, nullable=False, server_default=text("'[]'::jsonb"))
```

`UNIQUE(source_id, external_id)` 是整个幂等设计的根。它有两个连带效果，都值得提前知道：

1. **同一个 external_id 在不同来源下可以共存**。36氪和 InfoQ 都报道同一条新闻，各自有独立的 external_id，两行都保留。这正是「多源印证」需要的数据形态。
2. **它的粒度决定了去重粒度**。如果你把 `external_id` 取成 URL 而不是 RSS 的 guid，同一篇文章在来源改标题后的新 URL 会被当成新文档。这是取舍：guid 更稳，URL 更通用。我的选择是「guid 优先，缺 guid 回落 canonical_url」。

`topics` 和 `quality_flags` 用 JSONB 而不是关联表，因为阶段 1 只做筛选不做统计聚合；等到需要「按领域统计趋势」时再考虑拆表或建索引。**过早拆表是典型的小项目过度设计**。

## 2.3 SQLAlchemy 2 的写法与几个语法点

```python
from sqlalchemy.orm import Mapped, mapped_column

title: Mapped[str] = mapped_column(Text, nullable=False)
summary: Mapped[str | None] = mapped_column(Text)          # 可空
published_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
```

- `Mapped[T]` 是类型注解，SQLAlchemy 2 据此推断列类型并做类型检查；`Mapped[str | None]` 等价于可空列，不用再写 `nullable=True`
- `mapped_column(Text)` 显式指定列类型。PostgreSQL 里 `Text` 和 `String(255)` 性能几乎没差，而 `Text` 不会因为长度限制在某天悄悄截断
- `server_default=text("'B'")` 是**数据库侧默认值**，与 `default=` （Python 侧）不同。选 `server_default` 的好处是：直接 `INSERT` 裸 SQL 或由别人写脚本插数据时，默认值也生效
- `func.now()` 是数据库时间，`datetime.now()` 是应用进程时间。**时间戳优先用数据库时间**，避免多机部署时时钟不一致

## 2.4 异步引擎与会话

```python
# apps/api/app/db/session.py
engine = create_async_engine(
    settings.database_url,
    pool_pre_ping=True,     # 取连接前 ping 一下，避免拿到已被服务端关闭的死连接
    pool_size=5,
    max_overflow=10,
    echo=False,             # 调试 SQL 时临时改成 True
)

SessionLocal = async_sessionmaker(bind=engine, expire_on_commit=False, autoflush=False)
```

两个参数解释：

- **`expire_on_commit=False`**：默认行为是 commit 后让对象属性失效，下次访问会重新查库。在异步环境下这个"隐式查库"会触发 `MissingGreenlet`。关掉它，commit 后对象仍然可读。
- **`autoflush=False`**：默认 flush 会在每次查询前把待写对象刷到库里。在批量写入场景下这会带来意外的部分写入。手动控制 flush 点更安全。

会话有两种用法，别混：

```python
async def get_session() -> AsyncIterator[AsyncSession]:
    """FastAPI 依赖注入：请求结束自动关闭。"""
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise


@asynccontextmanager
async def session_scope() -> AsyncIterator[AsyncSession]:
    """脚本/任务：显式提交，异常回滚。"""
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

**API 里用 `get_session`，脚本和 Celery 任务里用 `session_scope`。** 前者的生命周期由框架管，后者需要明确的提交边界。

还有一个容易忽略的点：**API 进程和 Worker 进程各持有独立连接池，不能跨进程复用 Session**。Celery 任务里每次跑完要 `await dispose_engine()`，因为 `asyncio.run()` 每次创建新事件循环，asyncpg 的连接绑定在旧循环上，不复用会报 `attached to a different loop`。

## 2.5 Alembic：为什么不写迁移会出问题

```bash
# 初始化（一次）
alembic init migrations

# 改完 models.py 后
alembic revision --autogenerate -m "add xxx"
alembic upgrade head
```

`env.py` 里两件事必须做：

```python
# 1) 从应用配置注入数据库 URL，不要写死在 alembic.ini
config.set_main_option("sqlalchemy.url", settings.sync_database_url)

# 2) 让 Alembic 看到所有模型（否则 autogenerate 认为"没有表"）
from app.db.base import Base
from app.db import models  # noqa: F401  导入即注册
target_metadata = Base.metadata
```

**`autogenerate` 的三个盲区**，必须知道：

1. **扩展不会生成**。`CREATE EXTENSION IF NOT EXISTS vector` 要手写进迁移脚本
2. **索引表达式容易丢**。用 `text("published_at DESC")` 这种表达式索引时，有时检测不到差异，要手动核对
3. **重命名会被识别成「删一列 + 加一列」**，直接跑会丢数据。改字段名时先让 autogenerate 生成，再手工改成 `ALTER TABLE ... RENAME COLUMN`

手工装扩展的写法：

```python
# migrations/versions/0001_init.py（节选）
def upgrade() -> None:
    op.execute("CREATE EXTENSION IF NOT EXISTS vector")
    # ... 建表
```

> ⚠️ 如果某天你改了模型但忘了写迁移，代码里查一个不存在的列会报 `UndefinedColumn`。养成「改模型 → 生成迁移 → 看一眼生成的 SQL」的习惯，而不是直接 `upgrade head` 了事。

## 2.6 Connector 抽象：先定契约，再写实现

```python
# apps/api/app/connectors/base.py（节选）
@dataclass(slots=True)
class CanonicalDocument:
    """统一情报条目（L1 标准文档层的输入形态）。"""
    source_key: str
    external_id: str
    url: str
    canonical_url: str
    title: str
    fetched_at: datetime
    content_hash: str
    summary: str | None = None
    content_text: str | None = None
    language: str | None = None
    region: str = "global"
    content_type: str = "article"
    published_at: datetime | None = None
    topics: list[str] = field(default_factory=list)
    rights_mode: str = "metadata_excerpt"
    quality_flags: list[str] = field(default_factory=list)


class BaseConnector(ABC):
    @abstractmethod
    async def fetch(self, cursor: str | None = None) -> FetchOutcome:
        ...
```

这个抽象的价值在**边界清晰**：

- Connector **不碰数据库、不碰 ORM**，只负责「抓 + 解析 + 归一」。因此它可以单测——喂一段 RSS 字节，断言产出几条、字段对不对，不用起数据库
- 失败向上抛 `UpstreamError`，**由采集服务决定**重试、降频、记健康。Connector 不知道自己会被重试几次

`SourceSpec` 是另一个细节：它把「Connector 需要哪些参数」从数据库模型里剥出来，用 `from_source` 类方法做投影。这样 Connector 不依赖 `Source` 这个 ORM 类的字段名，以后改表结构不会连带改一堆 Connector。

## 2.7 RSS 解析：feedparser 的五个坑

```python
# apps/api/app/connectors/rss.py（节选，解析部分）
def _build_document(self, entry, feed_language, fetched_at):
    raw_link = (entry.get("link") or "").strip()
    title = clean_html(entry.get("title"))
    if not raw_link or not title:
        return None                                  # 没有链接或标题的条目直接丢弃

    canonical_url = canonicalize_url(raw_link)
    summary = clean_html(entry.get("summary") or entry.get("description"),
                         max_chars=settings.summary_max_chars)

    published_at = (
        parse_struct_time(entry.get("published_parsed"))
        or parse_struct_time(entry.get("updated_parsed"))
        or parse_any(entry.get("published"))
        or parse_any(entry.get("updated"))
    )

    external_id = str(entry.get("id") or entry.get("guid") or canonical_url)
```

五个坑，按遇到的频率排序：

**坑 1：时间字段有四个，且都不保证存在。** `published_parsed`（已解析成结构体）、`published`（原始字符串）、`updated_parsed`、`updated`。优先级是「已解析的优先」，因为 `published_parsed` 是 feedparser 帮你处理过时区的。四个全取不到时**返回 None**，不要用 `fetched_at` 顶替。

**坑 2：`bozo` 标志位容易被误解。** `parsed.get("bozo")` 为真表示「解析过程中有异常」，但**不等于解析失败**——很多真实世界的 RSS 都不严格合规，feedparser 会尽力解析并给出条目。所以判断逻辑是：

```python
if not entries:
    if parsed.get("bozo"):
        raise UpstreamError(f"feed 解析失败（{parsed.get('bozo_exception')}）")
    logger.warning("empty_feed")   # 没有条目但不是解析错误：可能这源就是空的
```

只看 `bozo` 就抛错，你会把一半能用的源判死。

**坑 3：`entry.content` 的结构。** 它是列表，每项是 dict，正文在 `["value"]` 里。直接 `entry.content` 当字符串用会报 `AttributeError`。要 `try/except (IndexError, AttributeError, TypeError)` 兜住。

**坑 4：同一次响应里可能重复。** 有些源的 feed 会同时包含「最新」和「分类列表」两份数据，同一条出现两次。在单次响应内用一个 `set` 去重（按 `canonical_url`），否则会在同一批 `INSERT` 里撞唯一约束。

**坑 5：编码与解析要放到线程里。** `feedparser.parse()` 是同步阻塞函数，在异步代码里直接调会卡住事件循环。用 `await asyncio.to_thread(feedparser.parse, response.content)`。

## 2.8 HTML 清洗：不信任 feed 里的任何标记

```python
# apps/api/app/utils/text.py
def clean_html(raw: str | None, *, max_chars: int | None = None) -> str | None:
    if not raw:
        return None
    text = BeautifulSoup(raw, "html.parser").get_text(separator=" ")
    text = unicodedata.normalize("NFKC", text)      # 全角/半角、兼容字符统一
    text = _WHITESPACE.sub(" ", text).strip()
    if not text:
        return None
    if max_chars and len(text) > max_chars:
        text = text[:max_chars].rstrip() + "…"
    return text
```

三个要点：

- **`separator=" "`**：不加分隔符的话，`<p>第一段</p><p>第二段</p>` 会变成 `第一段第二段`，两个词粘在一起
- **`NFKC` 归一化**：把全角数字、连字、兼容字符统一。不做的话，搜索「ＡＩ」和「AI」是两个不同结果
- **`html.parser` 而不是 `lxml`**：这里只做去标签，标准库解析器足够，且不引入 C 依赖。`lxml` 留给需要 XPath 的复杂场景

`rights_mode` 是合规开关，取值决定存多少：

| 取值 | 含义 | 存什么 |
|---|---|---|
| `full_text` | 有明确授权 | 可存全文 |
| `metadata_excerpt` | 常规公开 RSS | 标题 + 短摘要 + 原文链接 |
| `link_only` | 只允许索引 | 标题 + 链接，不存摘要 |

默认值就是 `metadata_excerpt`，摘要截断到 600 字。**这不是排版参数，是法律边界**，所以放在配置里而不是散落在代码里。

## 2.9 URL 规范化：去重的第一步

```python
# apps/api/app/utils/urls.py（节选）
TRACKING_PARAMS = {"utm_source", "utm_medium", "utm_campaign", "spm", "fbclid", "gclid", "ref", "from", ...}

def canonicalize_url(url: str) -> str:
    parts = urlsplit(url.strip())
    if not parts.scheme or not parts.netloc:
        return url.strip()

    scheme = parts.scheme.lower()
    host = (parts.hostname or "").lower()
    port = parts.port
    netloc = host
    if port is not None and str(port) != DEFAULT_PORTS.get(scheme):
        netloc = f"{host}:{port}"

    path = parts.path or "/"
    if len(path) > 1 and path.endswith("/"):
        path = path.rstrip("/") or "/"

    kept = [(k, v) for k, v in parse_qsl(parts.query, keep_blank_values=True)
            if k.lower() not in TRACKING_PARAMS and not k.lower().startswith("utm_")]
    kept.sort()                                  # 参数顺序统一
    return urlunsplit((scheme, netloc, path, urlencode(kept, doseq=True), ""))
```

规范化解决的是「同一篇文章的六种写法」问题：

```
https://36kr.com/p/123?utm_source=rss
https://36kr.com/p/123/
https://36KR.com/p/123
https://36kr.com/p/123#comments
http://36kr.com/p/123
https://36kr.com/p/123?from=rss
```

不去规范化，同一篇会入库六次；去规范化但**删多了**，`?id=456` 这种真正决定内容的参数被删掉，两条不同的文章被当成一条。所以 `TRACKING_PARAMS` 必须是白名单式的**已知追踪参数列表**，而不是「看起来像追踪的都删」。

> ⚠️ 千万不要用「删除所有 query 参数」这种规则。新闻站的长尾 URL 经常靠 `?id=` 区分文章。

## 2.10 内容指纹：能用，但别指望它

```python
def content_hash(title: str, canonical_url: str, summary: str | None = None) -> str:
    """标题 + 规范化 URL + 摘要。不使用发布时间，避免同一文章因来源修正时间而被判为新文档。"""
    payload = "\n".join([normalize_title(title), canonical_url, (summary or "").strip()])
    return "sha256:" + hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

它解决的场景：**同一内容的多个 URL**（手机版 `/m/`、AMP 版 `/amp/`）。

它的局限必须清楚：

- 摘要里多一个标点，hash 就变
- 来源修正错别字后重新发布，会被当成新内容
- 它**不能**识别「不同来源报道同一事件」——那需要标题相似度或事件聚类（阶段 3）

在阶段 1 它只做辅助索引（`ix_documents_hash`），真正决定幂等的是唯一约束。**别让指纹承担它承担不了的职责**。

## 2.11 主题分类：先用规则，别急着上模型

归一化的最后一步是打领域标签。这一步最容易犯的错是「一上来就调 LLM」——成本、延迟、结果不稳定三个问题同时出现，而你还没建立起判断分类对不对的基准。

规则版就够用的原因：

```python
# apps/api/app/services/classifier.py（节选）
TOPIC_LABELS: dict[str, str] = {
    "ai-models": "AI 与大模型",
    "software-engineering": "互联网与软件技术",
    "startups-funding": "科技公司与创业融资",
    "industry-trends": "科技产业与商业趋势",
    "open-source": "开源项目与开发者生态",
    "policy-macro": "政策与宏观经济",
}

_ASCII_WORD = re.compile(r"^[a-z0-9.\- ]+$")

def _hit(text_lower: str, keyword: str) -> bool:
    if _ASCII_WORD.match(keyword) and keyword.isascii():
        # 英文按单词边界匹配，否则 "ai" 会命中 "said"
        return re.search(rf"\b{re.escape(keyword)}\b", text_lower) is not None
    return keyword in text_lower        # 中文没有空格，只能子串匹配
```

四个设计决定：

- **slug 用英文、label 用中文**。`ai-models` 是 API 参数和数据库里存的值，`AI 与大模型` 是给人看的。混用会导致「改文案把 API 参数改了」
- **英文按词边界匹配，中文按子串**。中文没有空格分词，`"模型" in text` 就够；英文不按边界会出现 `ai` 命中 `said`、`api` 命中 `rapid` 这类噪音
- **标题权重高于摘要**。标题里有「融资」，基本就是融资新闻；摘要里出现「融资」可能只是在讲行业背景
- **最多返回 3 个领域**。一条新闻同时打了 6 个标签，等于没打

**这个方案的局限必须知道，并且接受它。** 实际跑起来出现过这样一例：

> 标题「小米18曝光:起售价5699元,预计12月正式发布」被判成 `policy-macro`（政策与宏观经济）。

原因很蠢：「标准版」里的「标准」命中了政策类关键词「标准」。这类错误会一直存在，因为**中文多义词无法靠关键词表解决**。所以在数据层留了 `quality_flags` 和 `topics` 两个字段——标签不准时，它是「弱信号」而不是「事实」，前端也因此把领域标签做成可点选的筛选入口，而不是唯一分类。

什么时候该换成模型：当你需要判断「这条政策对某公司是利好还是利空」这种需要理解的问题时。那时规则版不该删，而是留作**快速路径和兜底**——模型超时或返回低置信度时，规则的结论比空值有用。

## 2.12 网络层：重试的正确姿势

```python
# apps/api/app/connectors/rss.py（节选）
RETRYABLE_STATUS = {408, 425, 429, 500, 502, 503, 504}
MAX_ATTEMPTS = 4

def _retry_after_seconds(response) -> float | None:
    raw = response.headers.get("Retry-After")
    if not raw:
        return None
    try:
        return min(float(raw), 60.0)      # 上游让你等 3600 秒？只等 60 秒，剩下靠下一轮
    except ValueError:
        return None

def _wait_strategy(state) -> float:
    """有 Retry-After 就听上游的，否则指数退避（2s→30s 封顶）。"""
    exc = state.outcome.exception() if state.outcome else None
    if isinstance(exc, RetryableUpstreamStatus) and exc.retry_after:
        return exc.retry_after
    return wait_exponential(multiplier=1, min=2, max=30)(state)

async def _request(self, client):
    async for attempt in AsyncRetrying(
        stop=stop_after_attempt(MAX_ATTEMPTS),
        wait=_wait_strategy,
        retry=retry_if_exception_type((httpx.TimeoutException, httpx.TransportError, RetryableUpstreamStatus)),
        reraise=True,
    ):
        with attempt:
            response = await client.get(self.spec.base_url)
            if response.status_code in RETRYABLE_STATUS:
                raise RetryableUpstreamStatus(response.status_code, _retry_after_seconds(response))
            return response
```

四个判断，每一个都是踩过之后才写对的：

**① 哪些状态码该重试。** `5xx` 是服务端问题，重试有意义；`408/425/429` 是「稍后再来」；`4xx` 里的 `401/403/404` 是**确定性的拒绝**，重试 4 次只是浪费 30 秒并让日志更难看。所以 `RETRYABLE_STATUS` 用显式集合，不用 `>= 500`。

**② `Retry-After` 要读，但要封顶。** 上游让你等一小时，你的 Worker 不该卡在那里。取 `min(上游值, 60)`，剩下的交给下一轮调度——反正下一轮 5 分钟后还会来。

**③ 超时不是可选项。** `httpx.AsyncClient` 不设 `timeout` 时用的是默认 5 秒，容易在慢站上误判失败。显式设 20 秒，并配 `follow_redirects=True, max_redirects=3`（RSS 地址经常 301）。

**④ 异常信息要保留底层原因。**

```python
except (httpx.TimeoutException, httpx.TransportError) as exc:
    # 保留底层 message：DNS 解析失败 / 连接被拒 / 代理不通 在这里能直接区分
    raise UpstreamError(f"{self.spec.source_key}: 网络请求失败（{type(exc).__name__}: {exc}）") from exc
```

这一行我改了两次才对。第一版写的是 `f"网络请求失败（{type(exc).__name__}）"`，结果日志里只有 `ConnectError` 三个字——DNS 失败、连接被拒、代理不通，三种完全不同的故障长得一模一样，排查只能靠猜。**错误信息不带底层原因，等于没有信息。**

## 2.13 幂等入库：让数据库来保证

```python
# apps/api/app/services/ingestion_service.py（节选）
from sqlalchemy.dialects.postgresql import insert

rows = _document_rows(source, outcome.documents)     # 转成 dict 列表，批内先去重
created = 0
if rows:
    statement = (
        insert(Document)
        .values(rows)
        .on_conflict_do_nothing(index_elements=["source_id", "external_id"])
        .returning(Document.id)
    )
    result = await session.execute(statement)
    created = len(result.scalars().all())
```

这段是整个系统的核心，三个细节：

**① 为什么不用「先查再插」。**

```python
# ❌ 错误示范：并发下必然重复
exists = await session.scalar(select(Document).where(...))
if not exists:
    session.add(Document(...))
```

两次采集同时跑（定时器重叠 + 手动触发），两个查询都会返回「不存在」，然后都插入。唯一约束会救你一次，但你会收获一个 `IntegrityError` 把整批任务打断。**幂等要在数据库层保证，代码只负责触发它。**

**② `.returning(Document.id)` 是统计新增数的关键。** `ON CONFLICT DO NOTHING` 配合 `RETURNING`，只有真正插入的行才会被返回。所以"返回了几行"就是"新增了几条"，不需要额外查询。`skipped = len(rows) - created` 自然得到。

**③ 批内先去重。** 同一次响应里如果有两条相同 `external_id`（见 2.7 坑 4），单条 `INSERT ... VALUES (...), (...)` 会在同一条语句里撞约束，PostgreSQL 会直接报错而不是跳过。所以入库前用 `set` 过滤一遍。

```python
def _document_rows(source, documents) -> list[dict]:
    rows, seen = [], set()
    for document in documents:
        if document.external_id in seen:
            continue
        seen.add(document.external_id)
        rows.append({...})
    return rows
```

## 2.14 健康状态机与「失败不能清数据」

```python
FAILING_THRESHOLD = 3

async def _record_failure(session, source, *, message, http_status, latency_ms):
    now = datetime.now(timezone.utc)
    source.last_failure_at = now
    source.consecutive_failures = (source.consecutive_failures or 0) + 1
    source.health_status = "failing" if source.consecutive_failures >= FAILING_THRESHOLD else "degraded"
    session.add(SourceHealthLog(source_id=source.id, checked_at=now, ok=False, error_message=message[:1000]))
```

状态转移规则：

```
unknown ──首次成功──► healthy
unknown ──首次失败──► degraded
healthy ──失败 1–2 次──► degraded
degraded ──再失败──► failing（连续 3 次）
failing ──任意一次成功──► healthy（连续计数清零）
```

为什么分 `degraded` 和 `failing` 两档？因为**偶发失败是常态**。RSS 服务器 502 一次、网络抖动一次，都会让采集失败。如果一次失败就报红灯，你会习惯性忽略红灯，然后真的挂了也看不见。3 次是经验值：约等于连续 15 分钟都拿不到数据（按 5 分钟一轮）。

「失败不能清数据」是一条硬规则，写在服务层注释里：

```python
async def sync_source(session, source, *, triggered_by="schedule"):
    """一次 sync 的完整语义：
    1. 建 run（running）；
    2. 调用 Connector 抓取解析；
    3. 按 (source_id, external_id) 幂等写入，重复条目只计入 skipped，不覆盖旧数据；
    4. 无论成败都回写来源健康与 health log，失败不掩盖旧数据。
    """
```

为什么强调这一条？因为一个常见但致命的实现是「同步前先 `DELETE FROM documents WHERE source_id = X` 再全量插入」。这样源一旦临时挂掉，你会把它历史数据全清空，页面上直接消失。而且这个 bug 在生产上表现为「数据时有时无」，极难复现。

## 2.15 调度：让每个源有自己的节奏

```python
# apps/api/app/worker/tasks.py（节选）
@celery_app.task(name="app.worker.tasks.dispatch_due_sources")
def dispatch_due_sources() -> dict:
    """Beat 每 5 分钟调用：把到期来源逐个丢进队列。"""
    result = asyncio.run(_dispatch_due())
    for source_id in result["due"]:
        sync_source_task.delay(source_id, "schedule")
    return {"dispatched": len(result["due"])}
```

到期判定是这段的核心：

```python
due = or_(
    Source.last_success_at.is_(None),                       # 从没成功过 → 立即采
    Source.last_success_at
    < func.now() - (literal_column("interval '1 minute'") * Source.poll_interval_minutes),
)
```

**为什么不用「Beat 每 30 分钟全量采一遍」这种简单做法。** 因为不同源的合理频率完全不同：快讯类 30 分钟、官方博客 6 小时、arXiv 每天。固定频率要么对快讯太慢，要么对慢源太浪费（还被对方封 IP）。

这套设计的三个好处：

1. **每个源按自己的 `poll_interval_minutes` 生活**
2. **Beat 只做派发，不做采集**。派发是毫秒级的数据库查询；采集是秒级的网络 I/O。混在一起会让 Beat 越来越慢，最终调度失真
3. **失败自动降频**（未实现，但结构已留好）：连续失败时把 `poll_interval_minutes` 调大，是加一行代码的事

> ⚠️ 踩过的坑：`func.make_interval(mins=Source.poll_interval_minutes)` 在 SQLAlchemy 里会抛 `TypeError`（`make_interval` 的关键字参数重载有冲突）。改成 `literal_column("interval '1 minute'") * Source.poll_interval_minutes` 才行。这类"看起来该能跑"的写法，一定要实跑验证。

**Celery 任务的异步桥接**也值得说清楚：

```python
@celery_app.task(name="app.worker.tasks.sync_source", bind=True)
def sync_source_task(self, source_id: str, triggered_by: str = "schedule"):
    result = asyncio.run(_run_sync(uuid.UUID(source_id), triggered_by))
    return result
```

Celery 任务是同步函数，内部用 `asyncio.run()` 驱动异步采集。因此**任务结束前必须 `await dispose_engine()`** ——每次 `asyncio.run()` 创建新事件循环，asyncpg 连接绑定在旧循环上，不释放会报「attached to a different loop」。这个报错在第二次任务时才出现，非常容易误判成偶发问题。

## 2.16 API 层：三个约定

**约定一：统一响应信封。**

```json
{
  "data": {},
  "meta": { "request_id": "uuid", "timestamp": "2026-11-17T10:00:00Z", "total": null, "next_cursor": null },
  "error": null
}
```

前端只需要写一次解包逻辑，所有接口都一样。`request_id` 在中间件里生成并回写响应头，出错时用户报「某某时间点出错了」，你直接按 id 搜日志。

**约定二：游标分页，不用 offset。**

```python
def _encode_cursor(sort_at: datetime, document_id: uuid.UUID) -> str:
    payload = json.dumps({"t": sort_at.isoformat(), "i": str(document_id)}, separators=(",", ":"))
    return base64.urlsafe_b64encode(payload.encode("utf-8")).decode("ascii")

def _decode_cursor(cursor: str) -> tuple[datetime, uuid.UUID]:
    try:
        payload = json.loads(base64.urlsafe_b64decode(cursor.encode("ascii")))
        return datetime.fromisoformat(payload["t"]), uuid.UUID(payload["i"])
    except Exception as exc:
        raise AppError("cursor 无效", code="invalid_cursor") from exc
```

游标里带 `(排序值, id)` 两段，查询条件是「排序值 < 上一页最后一个，或排序值相等且 id < 上一页最后一个」。**为什么必须带 id**：`published_at` 会重复（同一分钟的十条新闻），只按时间翻页会跳过或重复。

**约定三：排序键用 `coalesce` 兜住空值。**

```python
def _sort_at():
    return func.coalesce(Document.published_at, Document.fetched_at)
```

排序用「有发布时间就用发布时间，没有就用采集时间」，但**返回给前端的 `published_at` 仍然是原始的 null**，不伪造。前端显示「发布 未知 / 采集 2026-11-18 21:19」，用户一眼能看出这条的时间不可靠。

## 2.17 前端：Next 16 缓存组件下的正确写法

这一节是全篇最容易踩坑的地方，因为**写错了开发模式看不出来，部署时才失败**。


**③ 这样写还顺带带来了更好的体验。** 骨架（标题 + 筛选栏占位 + 卡片骨架）静态预渲染，数据流式补上。构建产物里路由标记从纯动态变成 `◐ Partial Prerender`：

## 2.18 日志：让每条错误能自己解释

采集系统是那种「跑着的时候没人看，出问题时才有人看」的服务。日志的目标不是好看，是**在出事那天能用三十秒定位**。

```python
# apps/api/app/core/logging.py（节选）
class JsonFormatter(logging.Formatter):
    """把日志输出为单行 JSON，便于后续接入采集与检索。"""

    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        # 白名单搬运结构化字段，避免把任意 extra 全量打出来
        for key in ("source_id", "run_id", "document_id", "duration_ms", "request_id"):
            value = getattr(record, key, None)
            if value is not None:
                payload[key] = value
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)
```

四个要点：

**① 单行 JSON，而不是多行文本。** 一行一条日志，才能被 `grep`、被 `jq` 处理、被日志采集器按字段索引。多行堆栈默认会被切碎成多条不相关的记录。

**② 字段用白名单，不用 `record.__dict__` 全量输出。** 全量输出会把 `args`、`exc_info` 这些内部对象也塞进去，日志体积翻倍，还可能出现不可序列化的值。

**③ 事件名用「动词过去式」，不用句子。**

```
sync_succeeded    sync_failed    empty_feed    api_startup    dispatch_due_sources
```

这样你可以直接 `grep sync_failed | wc -l` 统计失败次数，而不必写正则去匹配「同步失败了」这种自然语言。

**④ 失败日志必须带 `error` 字段。**

```python
logger.warning(
    "sync_failed",
    extra={
        "source_id": source.source_key,
        "run_id": str(run.id),
        "duration_ms": duration_ms,
        "error": message[:300],
    },
)
```

这一条是 2.12 那个「错误信息丢失」教训的直接产物。判断标准很简单：**把这条日志单独拿出来，能不能定位到具体原因？** 如果只有 `source_id` 和 `duration_ms`，你只知道「36氪 在 8 秒后失败了」，然后什么也做不了。

另外两个工程细节：

- **降噪**：`httpx`、`httpcore`、`asyncio` 的日志级别调到 `WARNING`。不调的话，一次采集会打出几十行 HTTP 请求明细，把真正的业务日志淹掉
- **进程内只配置一次**：uvicorn 和 celery 各自会配 handler，不加重入保护会出现「同一条日志打印两遍或三遍」

`request_id` 是串起接口日志与采集日志的线索：中间件为每个请求生成一个，写进响应头，也写进日志。用户报「刚才那个页面出错了」，你按这个 id 搜，能看到从 HTTP 入口到数据库的完整路径。

## 2.19 怎么证明它真的对

跑起来不算完。下面是我实际用来验收的五种检查，每一种都抓到过问题。

**① 单元测试覆盖「易错但纯函数」的部分。** 25 个用例，重点是 URL 规范化、日期解析、HTML 清洗、主题分类，以及 RSS 解析的合约（含 429 重试、404 不重试两种情况，用 `respx` 模拟响应）。

```python
# 例：断言 4xx 不重试
@respx.mock
async def test_4xx_not_retried():
    route = respx.get("https://example.com/feed").mock(return_value=httpx.Response(404))
    with pytest.raises(UpstreamError):
        await connector.fetch()
    assert route.call_count == 1        # 只请求一次，不重试
```

**② 幂等性验证：同一批数据采两次。**

```
第一次：36氪 抓取=30  新增=30  跳过=0
第二次：36氪 抓取=30  新增=0   跳过=30     ← 新增必须为 0
```

这一条如果不过，后面所有统计都不可信。

**③ 边界用例要主动构造。** 坏游标返回 `400 invalid_cursor`，不存在的来源返回 `404 not_found`。不做这一步，前端永远拿不到确定的错误码，只能显示「加载失败」。

**④ 数据质量抽查。** 用 SQL 看分布，而不是只看总数：

```sql
-- 每个源的时间覆盖率与质量标记率
SELECT s.source_key,
       count(*) AS docs,
       count(d.published_at) AS with_pub,          -- 有多少条有真实发布时间
       count(*) FILTER (WHERE jsonb_array_length(d.quality_flags) > 0) AS flagged
FROM documents d JOIN sources s ON s.id = d.source_id
GROUP BY 1 ORDER BY 2 DESC;
```

「245 条里有多少条没有发布时间」这个数字，比「245 条」本身有用得多。

**⑤ 端到端链路验证（Celery）。** 不只看函数返回值，要看数据库里真的多了一条 `triggered_by='manual'` 的 run 记录。这说明 `POST → Redis → Worker → 入库` 整条链通了，而不是只测了其中一段。

# 第 3 阶段（手册阶段 2）多源 API：设计与要点

> 🔧 **状态说明**：本阶段**尚未实现**。以下是设计要点和必须提前想清楚的问题，不是实现记录。

## 3.1 为什么 API 比 RSS 难

RSS 是「给你一个 XML，你自己解析」。API 引入了四个新问题：

| 新问题 | RSS 的情况 | API 的情况 |
|---|---|---|
| 限流 | 一般宽松，429 少见 | GitHub 未认证每小时 60 次，超了直接 403 |
| 鉴权 | 无 | Token 放 header，可能过期 |
| 增量 | 不支持，每次全量 | 支持 `since` / `until` 参数或 ETag |
| 分页 | 一次给完（或只给最近 N 条） | 游标/页码，必须自己翻完 |

## 3.2 限流：读响应头，不要猜

GitHub 的做法值得当成模板：

```
x-ratelimit-limit: 60
x-ratelimit-remaining: 12
x-ratelimit-reset: 1763500000     ← Unix 时间戳
```

正确做法是**每次请求后把 `remaining` 记下来**，低于阈值（比如 5）就主动停手，等 `reset` 时间过了再来。而不是「失败了再退避」——配额用光后所有请求都是 403，退避没意义。

设计上需要在 `sources` 表加两列：`rate_limit_remaining`、`rate_limit_reset_at`。这样调度器能在派发前判断「这个源现在还有配额吗」。

## 3.3 增量：三种机制，优先级不同

| 机制 | 怎么用 | 适用 |
|---|---|---|
| `since` 时间参数 | 记住上次成功的 `published_at`，下次带上去 | GitHub events、arXiv |
| ETag / If-None-Match | 服务端算内容指纹，没变返回 304 | Hugging Face、多数 REST |
| 游标（next_cursor） | 服务端给下一页的 token | Hacker News |

三种可以叠加：先用 ETag 判断整体有没有变，变了再用 `since` 拉增量。

需要在 `sources` 表加一列 `sync_cursor`（文本），存每个源自己的游标/时间戳。**不要用「全局最后同步时间」**，因为不同源进度不同，一个源卡住会拖累所有源。

## 3.4 四个源的具体注意点

| 源 | 接口 | 关键约束 | 频率 |
|---|---|---|---|
| GitHub | `/repos/{owner}/{repo}/events` | 未认证 60 次/小时；必须读 `x-ratelimit-*` | 6–24 小时 |
| Hugging Face | `/api/models?sort=lastModified` | 支持 ETag；分页用 `cursor` | 6–12 小时 |
| Hacker News | Firebase API `/v0/topstories.json` | 无正式限流但别打太快；只同步新条目和分数变化 | 15–30 分钟 |
| arXiv | `/api/query?search_query=...&start=0` | **要求 3 秒间隔**，官方明确写在文档里 | 每日 |

arXiv 那条要特别小心：官方要求请求间隔 3 秒，不遵守会被封。这意味着「一次拉 100 条」要分 100 次请求 × 3 秒 = 5 分钟。**采集任务要能跑 5 分钟以上**，不能按秒级任务设计超时。

## 3.5 验收标准

- [ ] 至少 8 个来源可持续同步，`make status` 全部有 `last_success_at`
- [ ] GitHub 配额耗尽时，任务优雅停止并记 `degraded`，不是报错刷屏
- [ ] 同一个源连续同步两次，第二次抓取数明显小于第一次（增量生效）
- [ ] 所有源共用同一套 Connector 接口，新增一个源只需加一个文件 + 一行注册

# 附录 A 真实踩坑清单

全部来自本项目实际调试，按「现象 → 根因 → 修法」记录。这份清单比正文更值得常翻。

| 现象 | 根因 | 修法 |
|---|---|---|
| `make: *** [Makefile:15: up] Error 126` | WSL 里 docker 客户端被 PATH 上优先命中的 wrapper 抢占，那个 wrapper 调 `docker.exe` 需要 WSLInterop | 从 PATH 摘掉 wrapper 目录，直接用 `/usr/bin/docker` 原生客户端 |
| `exec docker.exe: Exec format error` | WSL 的 `binfmt_misc` 里没有 `WSLInterop` 条目 | Quit Docker Desktop → `wsl --shutdown` → 重开；或临时注册 `/proc/sys/fs/binfmt_misc/register` |
| 每条命令前刷两行 `RuntimeWarning: Unexpected value in sys.prefix` | Makefile 用 `../../.venv/bin/python` 相对路径，Python 3.14 解析出的 prefix 与 `pyvenv.cfg` 不等 | 用 `ROOT := $(CURDIR)` 拼绝对路径 |
| `ConnectionRefusedError (127.0.0.1, 5432)`，但代码没改过 | Docker Desktop 重启后容器 `Exited (255)`，`restart policy=no` 让它永不自愈 | compose 加 `restart: unless-stopped` |
| 采集报 `网络请求失败（ConnectError）`，无法判断原因 | 代码只写 `type(exc).__name__`，丢了底层 message | 异常包装保留 `str(exc)`，日志加 `error` 字段 |
| `TypeError` 来自 `func.make_interval(mins=...)` | SQLAlchemy 对该函数的关键字参数重载有冲突 | 改用 `literal_column("interval '1 minute'") * poll_interval_minutes` |
| `next build` 报 `blocking-prerender-dynamic` | `cacheComponents` 下 `searchParams` / `no-store` fetch 在 Suspense 外 | 数据获取下沉到子组件并用 `<Suspense>` 包裹 |
| 页面字体不是 Geist | `globals.css` 里 `body { font-family: Arial }` 覆盖了 CSS 变量 | 改为 `var(--font-sans)` 并补中文回落 |
| `MissingGreenlet` 出现在看起来无关的位置 | 在无 await 的上下文里访问了需要 I/O 的 ORM 属性；或 `expire_on_commit=True` 导致 commit 后隐式查库 | 设 `expire_on_commit=False`；在异步上下文里做 I/O |
| 第二次 Celery 任务报 `attached to a different loop` | `asyncio.run()` 每次新建事件循环，asyncpg 连接绑定旧循环 | 任务结束前 `await dispose_engine()` |
| 用 `app.routes` 枚举不到新加的路由 | FastAPI 0.163 的 `include_router` 是懒展开 | 用 `TestClient` 实发请求验证，别数路由 |
| 同一篇文章入库两次 | URL 带不同追踪参数；或 RSS 响应内部本身重复 | URL 规范化 + 单批内 `set` 去重 |
| 某个源每次都是「新增 0」但没报错 | `external_id` 取错（比如取成 URL，而站点每次带新参数） | 优先用 RSS 的 `guid`/`id`，回落 URL |

# 附录 D 术语表

| 术语 | 一句话解释 |
|---|---|
| Connector | 一个来源一个适配器，负责「抓 + 解析 + 归一」，不碰数据库 |

| 幂等 | 同一操作执行多次与执行一次结果相同 |

| 部分预渲染 (PPR) | 页面骨架静态生成，数据部分流式补上 |
| 运行时数据 | 只能在请求时获取的数据（`searchParams`、`cookies`、`no-store` fetch） |
| 健康状态机 | `unknown → healthy / degraded → failing` 的状态转移规则 |
| 退避 | 失败后按指数增长间隔重试（2s、4s、8s…） |
| `Retry-After` | 服务端告诉你「多少秒后再来」的响应头 |
