# 阶段 9：抽取期宾语形状校验

> 目标只有一个：让「宾语根本不是这个谓词该有的东西」这类错误**写不进去**。
> 不改表结构，不加迁移，不回补历史。

## 1. 为什么放在抽取入口，而不是修复档

`scripts/repair_facts.py` 的模块文档早就写了这条结论：泛称宾语的正确处理是**在抽取期用
`object_type` 挡掉，不为它回补历史**；`benchmark` 谓词整条不进任何档。

按这条结论，把它加进修复档等于给一个已经正确的决定再实现一遍，而且会让「`benchmark`
整条不进」的排除失效。所以这一步只动一处：`to_fact` 的校验链。

## 2. 判据只有一份

`apps/api/app/services/predicate_specs.py` 末尾：

```
def object_shape_problem(predicate: str, object_text: str) -> str | None:
```

它按 `PredicateSpec.object_type` 选规则，**不看谓词名**。`fact_extraction.to_fact`
在长度校验之后调它一次，命中就返回原因码，和 `too_long`、`malformed` 同级。

`PredicateSpec` 那次「两张表漏一个谓词」的教训是：同一件事写两遍，早晚漏一遍。
所以这里没有第二份规则表。

## 3. 拦什么

| object_type | 规则 | 原因码 | 真实样本（取自基线） |
|---|---|---|---|
| `product` / `benchmark` | 数量短语 | `object_is_quantity_phrase` | `30 个库`、`7 款新模型`、`18 public datasets` |
| `benchmark` | 泛称榜单或评审团 | `object_is_generic_ranking` | `leaderboard`、`LLM judges panel`、`榜单` |

判据全落在宾语自身的形状上，不需要读原文——这是它能放在抽取入口的前提。凡是要看原文
才能判的（比如「这个宾语是不是主语自己」），不属于这一步。

## 4. 为什么量词是必需的

数量规则要求「数字 + 量词 + 少量汉字」。量词不能省，这是整个规则里最容易写错的地方：

| 宾语 | 省掉量词会怎样 | 实际是什么 |
|---|---|---|
| `20 周年纪念版` | 被误判成数量 | 正常产品名 |
| `2026年` | 被误判成数量 | `founded` 的合法宾语 |

误杀比漏拦更贵：被拦掉的事实不会有第二双眼睛看见，而漏掉一条只是回到今天的样子。

## 5. 不该拦的

`version`、`year_or_org`、`scale`、`amount` 四种类型**整类排除**，它们的宾语本来就该以
数字开头：

```
1.30.7                 版本号
2026                   创立年份
1000 人                裁员规模
2.7亿元回购专项贷款     金额
```

测试里对每一条都钉了用例（`tests/test_object_shapes.py` 的
`test_keeps_legitimate_objects`），因为这几条是唯一会被「数字开头」规则误伤的地方。

## 6. 被丢掉的要能看见

`extract_facts.py` 新增 `rejected_object_shape` 计数，逐条打印被丢掉的宾语：

```
[3] x 宾语形状不符（object_is_quantity_phrase）：30 个库
```

只计数不打印的话，日志里「模型这次没抽」和「校验拦掉了」长得一模一样，而这批里恰恰可能
误杀真正的产品名。摘要行也加了 `宾语形状不符 N 条`，比例高时打一句提示。

## 7. 明确不处理的两条

| 样本 | 为什么不做 |
|---|---|
| `Metacritic` / `Metascore` 当 `benchmark` | 评分聚合站，需要知道「这是什么站」，没有形状判据 |
| `Alder Lake` 当被测基准 | CPU 代号是测试平台，需要领域知识 |

硬编码一份这样的词表，就是照着已有样本拟合：下一个 `Geekbench`、`Zen 5` 照样漏，还多了
一份要维护的名单。留在这两条不动，比做一个看起来能用的词表诚实。

## 8. 遗留

库里已有的 `released --> 30 个库` 还在，新规则只管以后写入的行。要清掉需单独撤回一次
（`repair_facts.py retract`），暂不处理——`released` 谓词的宾语约定本身还是模糊的，单清
一行不解决根因。

## 9. 测试

`apps/api/tests/test_object_shapes.py`：18 条。

- 该拦的拦：样本全部取自 `docs/数据品质基线.md` 的真实行，不是编的例子；
- 不该拦的不拦：`1.30.7`、`2026`、`1000 人`、`2.7亿元…`、`20 周年纪念版`；
- 规格表里没有的谓词一律放过（没有声明的类型，就无从判形状）。

## 10. 第二步：库层防护（2026-11-23）

第一步的校验只在写入前一瞬生效。绕过 `scripts/extract_facts.py` 直接写库，
或者将来新增一个入口，都会绕过它。第二步把同一份判据前移进库：

| 防护 | 实现 | 覆盖范围 |
|---|---|---|
| 谓词闭集 | `ck_fact_claims_predicate_closed_set` | 新写入的行 |
| 宾语类型合法 | `ck_fact_claims_object_type` | 新写入的行 |
| 宾语类型可审计 | `fact_claims.object_type` + 回填 | 全部历史行 |

**两条约束都是 `NOT VALID`。** 这不是省事：存量里可能有词表外的谓词，
加 VALID 会让迁移直接失败；而 NOT VALID 的表达正好是「新规则从今天生效，
存量另行清理」。状态写在 `pg_constraint.convalidated` 里，一眼能看出哪条还没验过：

```sql
select conname, convalidated from pg_constraint
where conrelid = 'fact_claims'::regclass;
```

**`object_type` 为什么必须落库**：形状校验按它选规则。不落库的话，事后审计
只能拿当前版本的 `SPECS` 反推——而 `SPECS` 会改，历史行当初按什么判的就丢了。
这和 `valid_from_source` 是同一类问题：**判断的依据必须和判断的结果一起存下来。**

**第一次升级失败：revision id 撞上 `varchar(32)`。** 迁移头的 id 是 30 字符，
按「头 + 后缀」拼出来 45 字符；`alembic upgrade` 一路执行完加列、回填、两条约束，
最后 `UPDATE alembic_version SET version_num=...` 才抛
`StringDataRightTruncation`，事务整体回滚。表现是两件看似无关的事：

```
value too long for type character varying(32)          ← 版本表写不进去
sqlalchemy.exc.ProgrammingError: column fact_claims.object_type does not exist
```

第二条不是「迁移没跑」，而是第一条的后果——DDL 已经被回滚了。教训是
**失败点可能在最后一步**：前面的成功输出不代表这一轮有半步落地。修法是把
revision id 改成 `0014_fact_claim_object_type`（27 字符），并加一条测试遍历所有
迁移断言 `len(revision) <= 32`。

**没做的两件事，各有原因：**

1. `object_entity_id` 仍然为空。列早就在（迁移 0005），但宾语从未被解析成实体。
   要让唯一约束比实体而不是文本，得先做宾语实体链接——那是另一件事，
   不是改个约束能解决的。
2. 存量脏宾语不自动删。`released --> 30 个库` 这类还在，清它们要逐条判断
   「撤回还是补新行」。`scripts/audit_fact_schema.py` 只出清单，不动数据。

**存量清理（2026-11-23 实跑）**：库层约束装上之后，审计脚本扫了全部未撤回事实：

```
未撤回事实 334 条
谓词不在闭集      0 条
宾语类型与规格不符 0 条
宾语形状不合规    7 条
```

前两项为 0 是**回填映射与规格表一致**的直接证据：`object_type` 的 CASE 是从
`PREDICATE_SPECS` 生成的，任何一处漂开都会在这里出现非零。第三项的 7 条是规则
生效前写入的存量，逐条判断如下：

| 事实 | 原因码 | 为什么算错 |
|---|---|---|
| `TriAgent --benchmark--> blinded judges panel` | `generic_ranking` | 评审团说的是「谁评的」，不是「哪个基准」 |
| `TriAgent --benchmark--> LLM judges panel` | `generic_ranking` | 同上，且与上一条同源同事件，一个事件被拆成两条事实 |
| `GRACE --benchmark--> 18 public datasets` | `quantity_phrase` | 数量不是基准名 |
| `AgentKombat --benchmark--> 模型与提示词公开排行榜` | `generic_ranking` | 泛称，没有专名 |
| `Software Factory --released--> 30 个库` | `quantity_phrase` | 数量不是产物名 |
| `WebCraft Pro --open_sourced--> 43 reusable Agent Skills` | `quantity_phrase` | 数量不是项目或仓库名 |
| `Gemini 4 Carbon --benchmark--> leaderboard` | `generic_ranking` | 占位词，读不出任何信息 |

**7 条全部撤回**，理由统一写成「宾语是数量/评审团/泛称榜单，不是该谓词要求的
基准名或产物名（信息保留在原文与 evidence 中）」。撤回后审计为 `327 / 0 / 0 / 0`。

**撤回不是删除**，三件事值得记下来：

1. 只写 `retracted_at`、`retracted_reason`、`retracted_replaced_by` 三列，行还在，
   原文和 `evidence_text` 也还在——`retract --undo` 能整条恢复。
2. **不释放唯一槽位**。`uq_fact_claims_identity` 上没有 `WHERE retracted_at IS NULL`，
   所以同一文档里再抽出同样的错宾语仍会被挡住。代价是撤回撤错了无法「重录」，
   只能在原行上 undo——这是刻意的取舍：错宾语不再进库，比能重录更重要。
3. 数字对账：事实总数 345、未撤回 334，差的 11 条是阶段 8 那批撤回记录。
   清理后再减 7 条得 327。**三个数字都能互相验证，没有孤立的口径。**

**为什么不写回「补新行」。** 这 7 条的正确形态需要重读原文才能确定产物/基准的
专名（`Software Factory` 到底发布了哪 30 个库）。补新行意味着一次新的抽取，
属于数据作业；而库里此刻的状态已经不是「错的被当成对的」，而是「错的被标成错的」——
后者是闭环，前者才是缺陷。
